# 技能槽位置分析（Astra）

依據：題目提供的實機資料，以及目前 HEAD `07e02cc` 的 CSS、HTML、JS。以下是靜態程式核對與幾何推算，沒有重新操作實機，也沒有改程式碼。新方案的尺寸是明示的設計假設，不冒充量測結果。座標單位皆為 CSS px；「舞台座標」與「螢幕座標」分開標示。

我的結論是搬離舞台，但不直接採用 A 的原始排列。推薦 D：直式把夥伴列移到舞台上方，舞台下方設固定技能列；橫式利用夥伴區右側設獨立技能區。兩者都讓技能與戰鬥熱區的交集為 0，直式也不必以犧牲拆包位置換取技能位置。

## 先核對題目前提

### 重疊成立，但 59% 與 56% 不是兩種版面的本質差異

CSS 最終生效的是：舞台無邊框；`#tap` 為 `[184,424] × [20,260]`；槽為 64×64，間距 16，底距 72，所以槽頂為 `360−72−64=224`。四槽如下：

| 槽 | 舞台 x 範圍 | 舞台 y 範圍 | 與 tap 的矩形交集 |
|---|---|---|---|
| 1 | 28..92 | 224..288 | 0 |
| 2 | 108..172 | 224..288 | 0 |
| 3 | 188..252 | 224..288 | 64×36 = 2304 |
| 4 | 268..332 | 224..288 | 64×36 = 2304 |

矩形交集通式為 `max(0,min(右緣)−max(左緣)) × max(0,min(下緣)−max(上緣))`。單槽比例為 `2304/4096=56.25%`，等比縮放不會改變比例。

橫式 `applyZoom()` 得到 1.25，960×640 居中後原點是 (40,30)，舞台原點是 (60,120)。因此 tap=(290,145)、大小 300×300；槽頂=400，槽 3、4 左緣=295、395，各與 tap 相交 `80×45=3600`。題目的橫式數字可完整重現。

直式左右 padding 各 8，所以比例是 `(390−16)/608=0.6151316`，不是 390/608。舞台高 221.447，原點約 (8,446.553)；tap=(121.184,458.855)，邊長 147.632；槽頂=584.342、邊長 39.368。槽 3、4 左緣=123.645、172.855，各交集為 `39.368×22.145=871.803`，仍為 56.25%。

題目的 `897=39×23` 恰好等於用整數框 `(459+148)−584=23` 算出的高度；因此它可以由先取整再相減重現，但不能當成精確面積。我沒看到原量測腳本，不能斷言其實作；若 897 是用未取整 DOMRect 算的，則需核對動畫時刻或執行中的樣式。至少目前原始碼不支持穩態比例由 56.25% 變成 59%。

### 「矩形重疊」不等於每一點都會放技能

`#game #tap { border-radius:0 }` 最終蓋掉前面的 30%，所以拆包是矩形；技能按鈕則是 `border-radius:50%`。`.skill-slot` 是 article，真正綁定發動的是子按鈕 `.skill-use`。`#slots > :not(.skill-slot)` 只排除其他直接子元素，沒有讓槽容器和槽間空隙自動穿透。

以 CSS 圓形邊界模型算，第三、四顆按鈕半徑 r=32、中心 y=256；tap 底緣 y=260，圓內被截取的面積是

`πr²/2 + 4√(r²−4²) + r² asin(4/r) = 1863.827`。

縮放到手機約 705.248 px²、橫式約 2912.230 px²。這是圓形按鈕的幾何模型，不是瀏覽器逐點命中實測；矩形角落可能落在 article 上，造成少算一次拆包，而非發動技能。另有 `disabled`、其他高層熱區及就緒時 scale(1.12) 動畫，實際命中需分狀態驗證。因此「重疊區全部技能贏」說得太滿；「有一大片可誤放技能的區域」仍成立。

`62s` 也不能直接解讀為每個技能誤放都損失固定 62 秒：`renderSlots()` 顯示的是剩餘冷卻，且剩餘冷卻大於 0 時按鈕 disabled。`clicker-balance.js` 有 45、60、90、120 秒等基礎冷卻。非對稱代價成立於技能就緒時；顯示 62s 的當下不會再次消耗它。幾何面積不能推成誤觸機率，仍缺玩家落點分布。

### 渲染位置與搬家清單有兩處需更正

實際槽渲染在 `src/clicker.js:235` 的 `renderSlots()`，不是 `clicker-stage.js`。空槽用同一顆 `.skill-use` 顯示「＋」，點擊進 `showRoster(null,i)`；沒有產生 `.slot-pick`。後者是 CSS 留存的樣式。`.slot-stamp` 則由 `clicker-stage.js:219` 加在夥伴卡上，不是槽內附件，不應整批跟著槽搬。

要搬的是 `.skill-use`、名稱、冷卻文字／圈、當家旗、tooltip 與空槽／鎖定狀態；另須處理槽外的連鎖提示及以槽為起點的特效。依據是兩個 render 函式的 `append` 與事件綁定，不是類別名稱猜測。

## 第一題：技能槽搬去哪？

為公平比較，先給新直式技能列一個一致規格：列高 72，四顆按鈕各 48×48、水平間距 16，總寬 `4×48+3×16=240`，垂直置中。48 是本方案選定值，不宣稱是量測出的最佳尺寸。相對現況矩形 39.368²，按鈕框面積由約 1550 增至 2304，增加約 48.7%。名稱與倒數改為在這 72 高內排版，不直接照搬向外突出的標籤。

390 寬時四顆 x 範圍為 75..123、139..187、203..251、267..315；320 寬時總寬仍小於可用 304，左右尚各餘 32。以 1.12 倍就緒放大算，48 會變 53.76，相鄰鍵間仍有 `16−5.76=10.24` 空隙，列內上、下原本各 12 的餘量各剩 9.12。

### A：單純加在舞台與夥伴之間——解重疊，但拆包被推得太高

新列加上一個 flex gap，增加 `72+7=79` 高。底端夥伴及分頁不動、留白尚未耗盡時，舞台從約 447..668 上移成 368..589，tap 中心從 533 變成 454。技能列為 596..668，按鈕 y=608..656、中心 632；tap 底緣約 528，與技能框垂直相隔 80，交集確為 0。

但 tap 中心距題目舒適區上緣 560 的差，由 27 增到 106。A 可以保護技能，不能聲稱整體連點體驗也改善。我不選它作最終排列。

### B：縮小／上移 tap——可算出需要付出的尺寸

只垂直分離，tap 底緣必須不超過槽頂 224。保持 top=20 時，高最多 204，手機高約 125.49；若縮成 204×204，面積剩 `(204/240)²=72.25%`，損失 27.75%。若只裁高度保留寬，則剩 85%，損失 15%，並非必然要兩軸一起縮。

保持 240 高而上移，需要 top≤−16，即上移至少 36 舞台 px，手機 22.14；tap 中心約從 533 降到 y=511。更會伸出舞台頂端約 9.84 手機 px，超過舞台與上一區只有 7 的間隔。最終 `#stage { overflow:visible }`，不能假設這一截自動裁掉。以上都是零安全間隔的臨界值；要留縫還得再縮／再移。

所以 B 不是做不到，而是在目前連點中心已高於 560 的前提下，再拿掉約 22px 的下側可點區，不如調整區塊順序。

### C：技能與夥伴共用滑動列——寬度帳不支持四技常駐

390 寬的 team 內部可用寬約 `374−4邊框−12內距=358`。四技列寬 240，再留 16 分隔，只剩 102 給夥伴，相當於一張 80 寬卡加 22 空間；320 寬時只剩 `288−240−16=32`，連一張卡都看不全。

若上下分層，卡高 88 加技能 48，即使不算間隔也有 136，已超過 100；原 team 內容高恰為 `100−4−8=88`。若所有項目共用橫向捲動，十張卡光寬度就有 `10×80+9×7=863`，加 240 技能後更無法保證四技同屏。因此不能同時滿足「100 高不變、夥伴照常展示、四技隨時可按」。這比「混在一起感覺容易誤觸」更直接。

### D：改操作群順序，保留獨立技能列——我的選擇

直式順序改為「錢包 → 留白 → 商店 → 夥伴 → 舞台 → 技能 → 分頁」。相較 A，舞台前增加原有的夥伴高與 gap，共 `100+7=107`，故舞台相對現況淨移動 `107−79=+28`，往下而非往上。

390×844 時：夥伴約 368..468、舞台 475..696、技能列 703..775、分頁 782..838。tap 約 y=487..635、中心 561；技能按鈕 y=715..763、中心 739。兩個中心都進入題目給的 560..780 區間，tap 與技能框交集為 0，垂直間隔約 80。

其代價是夥伴從 675..775 移到 368..468（上移 307），看卡／換人要向上移手。這是明確交換：把底部空間優先給不停點擊與即時施放，而非夥伴管理；是否值得由操作優先序決定，面積本身不能證明人的偏好。

## 第二題：橫式要不要一起改？

要。理由不是 56% 與 59%「差不多」，而是它們本來就是同一個 56.25% 矩形重疊問題。兩槽合計佔 tap 矩形 `2×2304/57600=8%`；滑鼠精確可能降低落入這 8% 的機率，但沒有點擊分布便無法量化「低很多」。更有第五題的王熱區遮技能問題，與手指粗細無關。

不建議橫式另塞 72 或 80 高的一整排：現有 stage 到 y=432、team 從 448 到 580、footer 從 592 到 624，縫只有 16、12、底部 16；不存在一條現成的 72 高空白。

推薦在 960×640 的 team 右側切出固定技能區，與左側夥伴在不同互動容器。具體幾何草案：

- 夥伴保留約 x=31..551 的 520 寬，五卡 `5×80+4×10=440` 放得下。
- 四技能沿用 64×64、間距 16，總寬 304，放在遊戲座標 x=600..904、y=480..544。
- team 範圍為 x=16..944、y=448..580，所以技能右側剩 40、底側剩 36，上方剩 32 可排標籤／連鎖資訊。
- tap 為遊戲座標 x=200..440、y=92..332；技能與其 y 間距 148，與正常舞台底緣 432 也有 48。交集皆為 0。

1280×860 下技能框會是 x=790..1170、y=630..710，tap 底緣 445，垂直間隔 185。960×640 原尺寸直接容得下，無須增大 exe 設計畫布。這仍是布局可容納證明，不是 exe 實機驗收。

此方案不能只改 CSS 寬度：目前 `setPartners()` 每頁切十人，十卡寬 `10×80+9×10=890`，塞進 520 必溢出。要一併改每頁五人（含頁數／翻頁／入隊定位）或只讓左區捲動；我偏向五人分頁，技能區永不跟著捲。原 `.buddy-header` 寬 900、分享入口 `left:604px` 也須重新分配，不能假設右半邊現在就是空的。

## 第三題：自成一列要在舞台上面還是下面？

選下面，但必須同時說清楚夥伴在哪。以下先鎖住其餘區塊，使用 72 高技能列與 7 間隔，比較插入位置；實機整數基線誤差約 1px。

| 排列 | 舞台 y | tap 中心 y | 技能列 y | 技能鍵中心 y |
|---|---|---|---|---|
| 現況：技能在舞台內 | 447..668 | 533 | 槽框 584..623 | 604 |
| 技能→舞台→夥伴 | 447..668 | 533 | 368..440 | 404 |
| 舞台→技能→夥伴（A） | 368..589 | 454 | 596..668 | 632 |
| 夥伴→舞台→技能（D） | 475..696 | 561 | 703..775 | 739 |

把列放上面時，雖新增了 79 高，卻剛好由前面的留白減少 79 抵銷，舞台不動；不能把所有元素一概往上扣 79。結果技能中心 404，比舒適區起點 560 高 156。放下面但不換夥伴順序，則技能改善、tap 惡化。D 才能在這個高度把兩者同時放進參考區間。

### 留白有多少，矮螢幕何時失效？

忽略 safe-area、以 CSS 浮點值計算：商店不是只有 `64×3=192`，還有兩個 8 gap，所以是 208；外層六個在流內的區塊（包括留白）產生五個 7 gap。既有最低需求是

`上下padding12 + 錢包60 + 商店208 + 舞台221.447 + 夥伴100 + 分頁56 + gaps35 = 692.447`。

故 844 高時留白有 151.553。新增技能列後七區塊、六 gaps，需求為 `692.447+72+7=771.447`，留白剩 72.553。safe-area 上下之和 S 會使門檻變成 `771.447+S`；寬度 W 的一般式為 `550+360(W−16)/608+S`。320 寬時門檻為 730；390 寬時約 771.45。

因此「矮螢幕先壓留白」只在門檻以上成立。390×667 時缺約 104.447；目前 body/game overflow hidden，留白歸零後不能憑空長出空間。頁尾還把狀態字絕對定位在 y=78、98，它們不吃 flex 高度，留白消失時可能蓋到上移的商店，也必須重新安置。

推薦的矮屏退路是把「錢包／商店／夥伴」放進可捲動的上方管理區，底下保留舞台、技能、分頁固定可見。以 390×667 為例，下方需求 `221.447+72+56+兩個gap14+底padding6=369.447`，舞台起點約 297.553，tap 中心約 383.671，技能列 526..598、鍵中心 562。上方扣頂 padding6 與分隔7 後剩 284.553，管理內容至少 `60+208+100+兩個gap14=382`，故需捲動至少 97.447。狀態字若另加行高還要再算。

這個退路保證控制不被裁掉，**不保證矮屏的 tap 仍在舒適區**。667 高若用同樣底部約三分之一規則，起點約 445，tap 中心 384 仍偏高；固定舞台、72 技能、56 分頁同時不縮，算術上就有這個限制。不能用 844 高的結論包辦所有手機。

## 第四題：不搬家是否能解？

可以改變誤觸後果，但手勢方案不會消除交集。

- **長按施放**：空間仍重疊每槽 2304 舞台 px²。假設門檻 τ=350ms，落在重疊區的 100ms 點擊不會放技，但若未轉送，也不會拆包；真正想打王施放則至少多等 350ms。它能隔開短點與施放，卻增加顯性延遲。350ms 是示例，不是從使用資料得出的最佳值；須處理取消、滑出及鍵盤等效操作。
- **連點期間收起 hit box**：若以最近一次點擊後 T=250ms 為封鎖窗，玩家每 200ms 點一次便永遠不解鎖，必須停手超過 250ms 才能放技。即時戰鬥操作因此多了停手條件。只對子按鈕設 pointer-events:none 也不夠：原 article 與整排容器仍在 y=224..288，上述 2304 交集或槽間隙可能繼續吞事件。
- **技能優先改成 tap 優先**：提高 tap 層級可把這塊矩形全部交回拆包，但等於拿走每顆重疊槽 56.25% 的矩形可用區。按圓模型，技能在 tap 以下只剩 `π32²−1863.827=1353.164`，即圓面積的 42.06%；手機只剩約 512 px²，且集中在高度約 `28×0.615=17.22` 的下側弓形區。能修誤放，卻把技能變成難命中的碎片。

真正純空間的「不搬 DOM」候選，是把槽在舞台內下移：槽頂至少 260 才不交 tap，即 bottom≤36；保留 12 舞台 px 間隔則槽頂 272、底緣336、bottom24。這能把 tap 交集歸零，但槽 4 的 x=268..332 會與子包 x=330..430、y=186..306 相交 `2×34=68`；正常王範圍也能覆蓋槽，且舞台底部還有計量條。這只是把衝突移給別的目標，並沒有得到一塊所有戰鬥狀態皆安全的專區。

因此我不採手勢／暫停 hit box 作主方案。拒絕的依據是上述保留的面積、縮掉的可點高度與必增的延遲，不是單純不喜歡隱藏規則。長按若將來由使用者自主選擇，可另作輔助防誤觸設定。

## 第五題：連帶影響有哪些？

### 1. 王與其他熱區：不該只比較 tap 的 z=5

`#targets` 本身 z=6、pointer-events:none，子按鈕恢復 auto；槽 z=9。`#boss-challenge` z=12；普通 `#boss-view` z=13 且本身可點，滿版王才降為 z=8。

| 物件（舞台座標、穩態） | 與舊槽的矩形關係 | 意義 |
|---|---|---|
| 子包 0：330..430 × 186..306 | 槽4相交 2×64=128 | 槽較高；移走會還出子包左側熱區 |
| 禮包：28..132 × 108..244 | 槽1交 64×20=1280；槽2交 24×20=480 | 「禮包在技能上方、不重疊」的舊註解與現有座標不符 |
| 預設王：330..590 × 60..360 | 槽4交 2×64=128 | 王 z=13 在槽上，並非技能永遠贏 |
| 灰狼王：204.5..595.5 × 60..360 | 槽3交 47.5×64=3040；槽4交 64²=4096 | 第4槽整個框被王熱區覆蓋，會打王而非放技能 |
| 滿版王：0..632 × 0..360 | 四槽框各交4096 | 靠 z=8 讓技能 z=9 留在上面 |

灰狼尺寸來源是 `clicker-scene.js` 的 width391、center400，故左緣 `400−391/2=204.5`；不能只用預設 width260 推論所有王。CSS 按鈕圓形、狀態與動畫會影響精確命中，但第四槽完全被灰狼矩形包住這件事不靠細小邊界差異成立。

挑戰鍵原始框 x=470..590、y=40..88，旋轉 −3° 後包圍框約 x=468.826..591.174、y=36.893..91.107，與槽最右332、最上224均分離；它不是這次技能重疊的來源。是否可見仍由挑戰／戰鬥狀態控制。

移到 D 的舞台外列後，正常戰鬥熱區底緣最多落在舞台底 696 左右，技能框715起，矩形交集歸零。滿版王雖橫向多出 `24×0.615≈14.76`，y仍到360，不會因此碰到技能列。這時不需要為了技能再提高 boss、targets 或 challenge 層級，也不應無故提高它們去遮其他目標。

但王血條不是框內：bottom=−16、height14，所以在舞台 y=362..376，手機畫面約697.78..706.40。它會伸進 D 技能列703..775的頂部約3.4px，尚未碰到按鈕715起點；若名稱擺在列頂便可能相蓋。應把血條收入舞台底部（例如舞台342..356），或明確保留其延伸空間；不能宣稱把槽移出後整個視覺區也自動完全分離。

### 2. 連鎖提示不在 slots 裡，照搬會飄到錯地方

`renderChain()` 將 `#chain-tape` 插在 slots 前面，然後用 `slots.offsetTop−52` 定位。現況舞台內是 y=172；若手機移到技能列後按鈕約 y=715，照舊減52會到663，回頭疊到舞台；若 DOM 先已建立 tape 再只搬 slots，兩者甚至會使用不同 offsetParent 的座標。

應把連鎖提示明確納入新技能區的資訊布局，重新選定定位基準；72 高中，48 按鈕上下共剩24，可安排上下各12的簡潔資訊行，名稱、倒數若選較大字需重算列高。這是方案條件，不是保證沿用現有字牌就放得下。

### 3. 神話特效有正確座標換算，但可能超出舞台

`clicker-stage.js:628` 起對青花、月月仙與萬物神話使用按鈕 DOMRect 轉回舞台座標：`(按鈕中心−舞台原點)×stage.offsetHeight/stageRect.height`。D 的 y 中心739、舞台頂約474.553，回算約429.903，大於舞台高360。這不是座標算法錯，而是技能真的已經在舞台外。

目前舞台 overflow:visible，所以特效能往外畫；若未來為限制滿版王而加 overflow:hidden，會裁掉這些從外部技能起飛的特效。需要選定獨立特效覆蓋層或把技能起點特效留在技能列。tooltip 也要調整：現有寬290，手機第4鍵 x267，右緣達557，比390寬超出167；移出縮放舞台後不能照用左對齊。

### 4. 搬 DOM 與互動狀態要一起驗，不要只換 left/top

槽仍保留同一個 id 可讓 `renderSlots()`、`activate()` 及特效查找繼續工作；不要為直橫建立兩組同 id、兩組發動事件。就緒、冷卻、空槽、未解鎖、抽卡與 cutin disabled 狀態都在 `renderSlots()`，搬家不能繞過。夥伴 `.slot-stamp` 仍屬卡片，應繼續跟隨夥伴列。

當槽離開 stage，原本針對 stage 直接子元素的 pointer-events 排除規則不再保護新列；應明確讓資訊牌／特效不吃點擊、按鈕可點，並確認槽間16px落空時不會觸發施放。層級也應低於招募、cutin、面板；不能靠把新槽 z-index 拉到最高解決遮擋。

另外已有一個值得分開追蹤的直式座標問題：`clicker.js:522` 等處仍以整個 game 的寬/960、高/640換算輸入，但直式實際是舞台自己的0.615縮放。取子包0中心舞台(380,246)，現況手機約(241.75,597.88)，舊換算後 x約595.08，再減16變579.08；它拿這個值與380／442／504比較會偏選第3包，而非第1包。這是既有的不一致，不是搬技能造成；調整舞台位置後更不能把所有落點偏移都歸咎於新布局。

## 最終推薦與取捨

選 D：直式「夥伴→舞台→72px獨立技能列」，橫式 team 右側固定四技、左側夥伴五人分頁。前者在390×844把 tap／技能中心放到約561／739，後者在960×640內以x600..904、y480..544容納四技；兩者與 tap 及王本體熱區的交集均可降為0。

接受的代價是：直式夥伴管理上移307px、可用留白少79px，低於約771.45px加safe-area的手機須讓上方管理區捲動；橫式夥伴每頁從十人減到五人。還需重排血條延伸、連鎖提示、tooltip和槽起點特效。這比 A 多動一個區塊、比 B 多動布局，但保留原 tap 面積，也不用靠施放延遲交換安全性。

後續若實作，驗收應以三種視窗（390×844、390×667、960×640／exe）核對新矩形、槽間隙與實際落點，再涵蓋空槽、就緒、冷卻、灰狼王、滿版王、禮包和四槽同屏。本文完成的是有尺寸依據的方案分析，尚未聲稱方案已通過這些實機驗收。
