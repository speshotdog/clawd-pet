**Q1．三套語言怎麼選**

先釐清原始碼：`ceremony.css` 的六層背景不是六層都亮著；`.stage-substrate`、`.stage-sheen` 目前為零透明度，`.stage-glow` 僅 `.025`。它的特徵是黑底、幾何、材質與留白，而不是滿畫面光效。另外，六角按鈕是末段 `.pull-actions button,#p10` 的覆寫，並非所有 `button` 都已六角化。

| 選項／規模／取決於 | 第一秒感受 | 資產與 CSS 成本 | 精裝卡是否融入 | 「不是換色票」驗收 |
|---|---|---|---|---|
| **抽卡延伸／中／無** | 從抽到力量，走進使用力量的世界；熟悉卡片，陌生環境 | 沿用近黑底、Noto Sans TC、`#eadfc4`、切角輪廓與內縮底板寫法；新增路線、節點、關卡景深。重寫畫面配置及互動樣式，不直接套 `.fan`、`.slot` | 最自然；卡面是環境裡最精細的材質 | 地圖場景與路線占畫面 **55～70%**；主操作中心相較 1.0 同任務画面的正規化位置移動 **20～40% 畫面對角線**。灰階下仍看得到結構改變 |
| **1.0 黑化／中／無** | 同一張熟悉桌面進入危險區域 | 可參考原資訊關係，但 `#game`、`.topbar`、`#shop`、`#team` 的固定位置仍須重排；另做暗色紙材與拼貼資產。若只重用原排版，成本低卻不達標 | 圓體、咖啡描邊與實心陰影可能把精裝卡襯成外來物件 | 場景占比 **55～70%**，紙材／貼紙占比 **10～20%**，主要操作位置位移 **20～40% 對角線**；達不到即只是暗色主題 |
| **第三套語言／大／無** | 像進入另一款遊戲，例如災後軍事終端 | 新字體層級、圖示、面板、按鈕、地圖、轉場皆需建立；僅保留卡面與一般容器模式 | 風險最高；若新介面偏平面，箔面卡容易像嵌入廣告 | 新輪廓／網格構成占非卡片 UI 面積 **65～85%**，完整精裝卡展示占編隊詳情區 **35～50%**；兩者須同時成立，不能靠藏卡達標 |

上述位置差異只證明結構有改，不能獨自證明好用。共同補一項辨識驗收：隱去版本名稱，讓玩家分類 1.0 與 2.0 截圖，正確率目標 **85～100%**；辨識耗時 **2～5 秒**。實際結果需要實機量。

**推薦抽卡延伸。** 延伸的是材質、字體、控制元件與深色留白；地圖不用整個召喚陣當背景，戰鬥也不重播揭卡演出。

另外兩個在以下情況會更適合：

- **1.0 黑化**：如果目標改成保持原桌面操作習慣、強調同一個寵物世界的恐怖續篇，且願意接受新設計感較弱。
- **第三套語言**：如果 2.0 未來成為獨立產品，已有足量一致的新場景與角色美術，足以支撐完整的第三套視覺系統。

**Q2．S1：先收起桌面，再揭開世界**

**方案：滿版遮幕跨座標系，沿用狀態驅動畫面的模式。規模：中。取決於：無。**

不要把 `#zoomer` 從縮放桌面一路拉成滿版。那會同時放大字、邊框與 PNG，最後仍要換成另一套排版。

轉場由獨立於 `#zoomer` 的滿版外層承接；舊舞台保持原縮放，遮幕完全不透明後，才切换到新的 `100vw/100dvh` 根容器。

| 順序 | 看得到的動作 | 提議驗收 |
|---|---|---|
| 收起舊控制 | 商店、隊伍及周邊介面先退場，城市暫留，讓玩家知道自己從哪裡離開 | **140～180ms**；視窗座標位移 **8～12px**；alpha 從 **1～1** 降至 **0～0** |
| 遮住座標切換 | 近黑遮幕覆蓋整個視窗，包括舊舞台外側 | **180～220ms**；覆蓋率 **100～100%**；終點 alpha **1～1** |
| 切換根容器 | 幕後切成滿版末世地圖；底層暫不可操作 | 完全遮蔽 **60～100ms**；舊 UI 穿透及誤觸 **0～0 次** |
| 先見土地與道路 | 遮幕退去，先出現廢墟地形和通往遠方的路 | **240～300ms**；場景由下方 **12～20px** 回到定位 |
| 再見現在與操作 | 當前節點、關卡名、編隊入口最後出現 | **160～220ms**；位移 **6～10px**；從場景出現後 **80～120ms** 開始 |

整體目標約 **0.70～0.92 秒**，不含素材等待。目的依序是「離開桌面 → 換世界 → 看清目的地 → 開始操作」。

素材應在揭幕前準備好；若準備失敗，顯示可返回的錯誤狀態，不能留在無提示黑幕。載入耗時**這需要實機量**。減少動態模式改為 **120～180ms** 淡換，位移 **0～0px**。

若舊 UI 退場以原舞台元素動畫實現，其局部位移須除以 `#zoomer` 實際縮放值，才能符合表中的視窗位移；不碰舊版排版常數。

**狀態設計：同模式，不共用抽卡控制器。規模：中。取決於：無。**

`ceremony.js` 的 `setScreen()` 明確只接受 `entry／ceremony／results`，並連動 `focus-held`、`updatePages()`。`updateFinish()` 還檢查卡片完成、動畫、計時器、rAF 與聲音是否全部結束。把地圖塞進去會錯誤繼承抽卡完成条件。

建議另設末世畫面控制器，以自己的 `data-screen` 管理地圖、編隊、一般戰、BOSS 戰與結算；轉場用自己的 phase。原抽卡三態及 `data-entry-phase` 原封保留。

可借鑑的契約是：

- `generation` 先失效，再取消舊工作。
- `wait()` 取消後要結束等待。
- `activeNow()`、`pauseTimers()`、`pauseRafs()` 的可見性處理。
- 背景生命週期與有限演出分開。

驗收：任意換頁或返回後，舊畫面回呼改動新畫面的次數 **0～0**；每次切換後可操作的主畫面數量 **1～1**。只隱藏 DOM 不算取消完成。

**Q3．S2：垂直前進，讓路線穿過不同地景**

**規模：中。取決於：無。**

採垂直捲動、局部左右偏移的單一路線。桌面右側放關卡摘要，手機則放底部。左右偏移只是地景構圖，不出現岔路或選路暗示。

| 元素 | 具體外觀 | 時間／位移／對比驗收 |
|---|---|---|
| 普通節點 | 切角地標牌，內有站序及地景符號；不用每站一顆光球 | 本體 **48～60px**；相邻中心縱距 **104～144px**、橫向偏移 **24～56px**；靜止位移 **0～0px**；輪廓與底色對比 **3～5:1** |
| 路線 | 單條折線沿廢墟延伸；已走實線，未走斷線 | 線寬 **2～3px**；已走線 alpha **.65～.80**，未走線 **.22～.34**；靜態時間／位移均 **0～0** |
| 當前位置 | 節點外切角括框，加「目前」文字及實心方向標 | 括框距本體 **6～10px**；對比 **5～7:1**；選中切換 **160～220ms**、位移 **0～0px** |
| 已通關 | 保留站名，加勾號及已完成實線；不整顆變灰消失 | 勾號 **14～18px**；圖形對比 **3～4.5:1**；標籤對比 **4.5～7:1**；靜止位移 **0～0px** |
| 未解鎖 | 空心節點、鎖形、前置站名；不顯示可挑戰按鈕 | 圖形 alpha **.30～.42**；標籤對比 **4.5～7:1**；選取摘要 **160～220ms** 淡換，位移 **0～0px** |
| BOSS 節點 | 寬幅城門剪影，路線穿過門中央，附 BOSS 字樣；不靠紅色辨識 | 寬 **88～112px**、高 **60～76px**；外形對比 **4～6:1**；待機位移 **0～0px** |
| 推進一格 | 舊節點落勾 → 連線向前填滿 → 當前括框移至新站 | 落勾 **120～160ms**；連線 **240～320ms**；新括框 **160～220ms**；峰值線 alpha **.78～.90** |

新節點已在視野內就不捲動；若被遮住，鏡頭只移到閱讀帶，單次移動 **12～28% 視窗高度**，耗時 **280～380ms**，不跳到畫面正中央遮斷上下文。

減少動態模式保留線型、文字與形狀差異，切換 **100～160ms**，追蹤移動 **0～0px**。這些 alpha 是呈現規格，並不能代替實際背景上的對比量測。

**Q4．S3：20 張應該能總覽，不必在所有裝置同屏讀完整卡面**

題目最需要調整的是「放進一個畫面」的意思。應驗收的是：**玩家看得到隊伍規模、能定位任一卡、能理解限制**，而非手機也硬塞完整卡面。

**① 四條累加限制先做好。規模：小。取決於：無。**

固定顯示四列，直接寫出集合：

- 神話：目前數量／2。
- 神話＋傳說：目前數量／6。
- 神話＋傳說＋史詩：目前數量／12。
- 全隊：目前數量／20。

每列搭配分段容量條、稀有度符號與文字。不要寫成四種獨立稀有度配額，也不要沿用 `CeremonyFx` 的稀有度顏色當唯一語意。

驗收：每列高 **24～32px**，文字 **13～15px**、對比 **4.5～7:1**。新增預覽會同時標示它影響的列；回饋在 **100～160ms** 內出現。

拖入超額傳說時：

- 原隊伍保持不變，卡片返回起點，耗時 **180～240ms**。
- 直接在第二列旁顯示「神話＋傳說合計已達 6，加入後將為 7」。
- 超額列邊框亮起 **240～360ms**，線寬 **2～3px**，對比 **4.5～7:1**；文字持續至下一次操作，不只閃一下。
- 若多條同時違規，全部標出，先說最直接阻擋的那條。

題目中的「第 7 張傳說」只是一個例子；已有神話時，會更早碰到第二條上限。驗收必須包括這種混合隊伍。

**② 編隊使用獨立版型。規模：中。取決於：無。**

不擴充 `CeremonyTable.layout`。

它目前不是拒絕 20 張，而是算出四排，卻仍以：

`(Math.floor(i/5)-.5)`

定位；卡寬與高度計算也仍以兩排為假設。後兩排會向下延伸。桌面卡寬還有 `170／190px` 下限，不能靠傳入較小高度自動縮成編隊總覽。

手機的 `position()` 又將非當前卡加上 `.page-away`，適合逐張欣賞，不適合隊伍比較。

新模組只負責編隊容器配置，與既有模組共用卡片身分及外部卡面呼叫方式；保留 `HoloCardFace.refit()`／`unobserve()` 的既有使用契約，不改卡面內部。`dealDuration:620`、`stagger(count===10?50:95)` 留在抽卡，不變成編隊逐張發牌。

建議配置：

| 情境 | 配置與驗收 |
|---|---|
| 寬螢幕總覽 | **10 欄×2 排**，卡寬 **88～104px**、比例維持 **5:7**、間距 **8～12px**；卡陣寬約 **952～1148px**、高約 **254～303px** |
| 中型桌面 | **5 欄×4 排**，卡寬 **88～104px**；空間不足時卡區獨立捲動，容量列與技能列保持可見 |
| 手機 | 隊伍代理圖採 **4 欄**，卡寬 **68～80px**；容器不足時降欄數，不繼續縮小；允許縱向捲動 |
| 詳情 | 選中後展示未修改的完整卡面，寬 **240～304px**；完整卡面容不下時改成詳情層 |

滿隊時出現的隊伍項目數量 **20～20**；任一卡的識別區被相鄰卡遮住的比例 **0～0%**。

**③ 總覽用卡片代理圖，詳情用完整卡面。規模：中。取決於：無。**

代理圖保留 **5:7 外形、角色主要輪廓、稀有度符號與外部姓名**。它是另一個 UI 項目，不是把凍結卡面的字級或 Z 改小。來源可用既有角色圖或完整卡面的靜態呈現，不另造角色姿勢。

完整卡面優點是忠實，缺點是縮小後文案難讀；純頭像最省空間，卻可能截掉角色的槌、角、身形等識別物。故不採一律裁臉。

驗收提案：

- 角色主要輪廓占代理圖面積 **45～70%**。
- 人工標記的關鍵識別部位保留率 **95～100%**。
- 外部姓名字級 **12～14px**、對比 **4.5～7:1**。
- 隱去姓名後配對原卡的正確率 **90～100%**，耗時 **2～4 秒**。

**68px 並不是已證實的辨識下限。這需要實機量。** 若達不到上述辨識率，就增大代理圖或減少欄數；不能只靠姓名替糊圖過關。

**④ 技能與隊伍相鄰，但關係不能先猜定。規模：中。取決於：技能來源、戰鬥自動或操作。**

四個技能格固定在隊伍區下方。格子高 **56～72px**、間距 **8～12px**，技能名稱維持可讀，不沿用 1.0 `#team` 的固定座標或 `.skill-slot select` 配置。

- **若技能來自隊伍卡**：技能格顯示來源卡小圖；選中時，來源卡与技能格使用相同括框。隊伍外卡不可成為有效來源。移除來源卡後必須明示技能缺額，不能靜默換人。
- **若技能為獨立池**：標示「獨立技能」，有自己的挑選入口；不畫連線、不重複隊伍序號，避免暗示必須由隊伍供應。

神話技能上限維持 1；另保留整組技能是否合法的訊息位置。但「不超過指定組合戰力」不能只靠稀有度數量推算，判定取決於後續技能戰力定義；未定前不要做虛構百分比條。

關聯高亮切換 **140～200ms**，框線對比 **4.5～7:1**。非法組合被顯示為可確認的次數 **0～0**。

**Q5．S4／S5：一般戰看交鋒，BOSS 戰看壓迫感**

**① 一般戰先建立穩定資訊區。規模：中。取決於：戰鬥自動或操作。**

畫面重心是敵我交鋒場景，下方是一條隊伍摘要與技能列。全部隊伍成員可在展開面板查閱；不把畫面上只顯示少數卡片解讀成「只有這些卡參戰」。

| 區域 | 提議驗收 |
|---|---|
| 交鋒場景 | 占可用畫面 **55～65%**；當次相關卡片可在事件位置短暫顯示 **1～3 張**，不暗示參戰名額限制 |
| 頂部資訊 | 占高度 **8～12%**；只放關卡名及已定義的戰況資訊 |
| 下方隊伍／技能 | 占高度 **20～28%**；點隊伍摘要可展開全部成員 |
| 事件卡片回饋 | **180～260ms**、位移 **8～14px**；不播放揭卡或稀有度爆光 |

自動戰鬥時，技能列顯示已定義的狀態；有操作時，同一區域承接可點技能，觸控目標 **48～64px**。冷卻、能量、目標選擇未定前不畫假的計量元件。

**② BOSS 戰改構圖，而非一般戰加大血條。規模：中。取決於：戰鬥自動或操作。**

BOSS 使用中央縱深構圖：上方識別區、中央怪物與專屬地景、下方隊伍。一般戰的左右交鋒構圖撤掉。

BOSS 場景占畫面 **65～75%**；一般戰與 BOSS 戰的主要焦點位置差 **15～25% 畫面寬度**。入場動作 **400～600ms**，背景位移 **16～28px**。鏡頭動，資訊列不晃。

不預設部位破壞、多階段血條、倒數時間或弱點游標。這些都不是單純的版面決策。

**③ 四種素材：統一展示規則，保留各自尺度。規模：中；去背部分大。取決於：無。**

以下依文件提供的素材描述提出，不把它當成已完成的圖像品質驗證。

| 素材 | 用法 | 驗收 |
|---|---|---|
| `01.gif` | 放在遠景平台中央，以大空間與場景尺度襯托小角色；不用模糊遮掩放大 | 圖像盒邊長 **144～180px**；依原圖為 **0.8～1.0 倍 CSS 尺度**。高像素密度螢幕是否仍清楚，需要實機量 |

尺寸按包含框量，不把透明留白誤算成角色身高；落地位置以輪廓最低接地點對齊。四個檔案不應強迫同樣動作頻率，也不應靠全體呼吸縮放遮掩靜態素材。

去背驗收用人工標記的角色／道具遮罩作參考：

- 主體遮罩覆蓋保留率 **98～100%**。
- 輪廓 IoU **.97～1.00**。
- 與原背景相連的殘留白區，面積占原背景 **0～0.5%**。
- 動畫各幀的處理誤差造成的面積比例波動 **0～2%**，並扣除原本動作引起的形變。
- 深色與中灰底均檢視，白色毛皮、槌柄、細角不能被當背景刪掉。

GIF 必須檢查合成後每幀，不能只驗第一幀。以上指標可允許零殘留；不為滿足「非零下限」而故意留下白底，也不用逐像素色差衡量抖色。

**④ 真・滅世珍獸：城市本來就是牠的一部分。規模：大。取決於：真身素材。**

`scenes.city` 的核心不是某個可裁出的角色，而是「整張城市圖就是王」。原始碼還記錄裁層失敗、鏡射拼寬造成對稱，最後只保留三棟暗樓當前景。因此不建議再靠自動裁原圖拼出真身。

新方向是：**城市輪廓其實是伏臥巨獸的背脊；到了 2.0，街道裂開，城市尺度才顯示出牠的形體。**

呼應方式：

- 延續原設定 `mat:'#4A3A2A'`、`sky:'#8A6B44'` 的暖色城市記憶，介面仍保留深色材質語言。
- 新背景重畫相似城市輪廓與前景暗樓；把地標形狀轉成背脊、冠部或外殼。
- 不直接沿用整張圖全亮一次；改以地平線錯位、城縫亮起、巨大陰影移動揭示真身尺度。

驗收提案：

- 從原城市確認 **2～3 個**地標，於新場景保留可辨識形狀；它們在指定對照區的輪廓保留率 **85～100%**。
- 真身／城市整體占主場景寬 **65～85%**。
- 開場揭示 **1.2～1.6 秒**，前景與遠景相對位移 **12～24px**。
- 裂縫亮帶占場景 **3～7%**，峰值 alpha **.45～.65**；主體識別輪廓可見率 **95～100%**。
- 衝擊只移背景 **3～5px**、持續 **160～220ms**，UI 位移 **0～0px**。

若拿到獨立透明真身素材，就讓牠從城市之後起身；若只有完整場景插畫，就採城市變形與遮罩揭露，不硬造可活動肢體。

戰鬥特效只借鑑 `ceremony.css` 的前後分層思路。既有抽卡平面順序 `2–7／8／10／20`、`runCanvasFx()` 的卡面避讓、`strengthen()` 的稀有度演出全部保留。**2.0 新特效採 CSS／DOM／SVG，不把既有 Canvas 抽卡特效搬成全站效果。**

**⑤ S6 與缺少的狀態。規模：小。取決於：失敗代價。**

六個畫面足夠，但 S1 是過程，S6 可作戰場上的結算層；不必都成為獨立頁面。

結算保留戰場上下文，背景遮罩 alpha **.45～.60**，結算區占畫面 **35～50%**，進場 **180～260ms**、位移 **8～12px**。只顯示真實發生的勝敗與獎勵；失敗代價未定前，不寫「無損」「扣除」或免費重試承諾。

缺少的是編隊內的卡片選擇／詳情，以及素材失敗、無可用精裝卡等狀態。這些放在既有畫面的局部層；任務測試中，不能返回或沒有下一步說明的死路數量 **0～0**。

**Q6．哪些不該做**

以下依「現在刪掉就能省下最多無效工作」排列。禁止項的 **0～0** 是明確缺席驗收；可見替代物另給有效範圍。

我會把後續派工順序定為：**地圖與關卡狀態 → 編隊可讀性及限制回饋 → 跨世界轉場 → 一般戰與 BOSS 構圖 → 真身資產與專屬特效**。戰鬥操作、失敗代價與技能戰力定義，等關卡骨架成立後再接入。

本題真正要先驗收的是：**看得出已進入新世界、找得到下一站、認得出隊伍成員、知道為什麼編隊被擋。** 這些成立後，才值得增加更昂貴的場景與特效。
