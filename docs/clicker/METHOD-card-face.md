# 卡面製作工法（第四十二～四十四輪定案）

給主專案、後續卡面開發、以及**其他對話**讀。這份不是某一輪的報告，是**可重複套用的做法**。

> **如果你是接手的另一個對話，先讀這三條，它們是這份文件裡最貴的教訓：**
>
> 1. **先去量現有做對的東西，不要自己推。** 使用者說「要像某張卡那樣」的時候，
>    去把那張卡的 computed style 全部 dump 出來。我沒這樣做，自己推論出一條
>    完全錯的路（用 translateZ 做視差），繞了好幾輪才發現人家根本沒這樣做。
> 2. **門檻沒先量基準就是無效門檻。** 驗證一條門檻有沒有效：拿「修正前的版本」去量。
>    修正前也不及格 → 是門檻或儀器的問題，不是實作的問題。這個錯我犯了三次。
> 3. **改了樣式先確認真的生效再開始量。** 好幾個版本量出來數字一模一樣，
>    那不是「改動沒影響」，是覆寫被特異性壓掉、或被父層的 `transform-style:flat` 壓平了。

逐輪的實測數字在 `REPORT-gift-round42.md`／`43`／`44`，這裡只留結論與理由。

適用範圍：`_art/holo-test/` 的卡面展示頁，以及之後把卡面搬進遊戲時的渲染選型。

## 一、卡面渲染：不要在執行期用動畫 `mask-image`

### 問題

反光層靠 `mask-image` 吃角色剪影。**`mask-image` 不走合成執行緒**，
遮罩每格都讓 600×840 的圖層整片重新光柵化。角色動畫是 30fps 90 格，
等於每 33ms 就整層重畫一次。

實測（同一台機器，三次取平均）：

| 做法 | fps |
|---|---:|
| 逐格遮罩 | 24.5 |
| 15fps 遮罩（每 2 格取 1）| 27.2 |
| 10fps 遮罩 | 28.3 |
| **完全不用遮罩** | **42.1** |

**降低遮罩更新率最多買到 +3~4 fps**，天花板是「完全不用遮罩」。
所以遇到這個瓶頸時，調遮罩參數是死路，要換工法。
（另外：粒子只值約 3 fps，不是主因；DPR 1 與 DPR 2 量起來一樣，跟螢幕解析度無關。）

### 三條替代路線與結論

| 路線 | 做法 | fps | 反光可校準到 ±15%？ |
|---|---|---:|---|
| R1 | 單一 canvas，`globalCompositeOperation='source-atop'` 疊反光 | 51.8 | ❌ 最好 16.15% |
| R2 | 反光層改用角色圖複本，靠 `filter` 鏈＋`mix-blend-mode` | 46.4 | ❌ |
| **R3** | **單一 three.js canvas，保留 alpha 的 shader** | **49.3** | ✅ **gain 0.87，12 姿勢最大偏差 13.80%** |

**三條的時間預算都達標，選型的決定因素是「反光還原度」不是 fps。**
R1 最快但單一純量增益收斂不了——誤差隨姿勢與 glare 變化，
掃到 1.112→1.116 只是把誤差在 −15.8% 與 +15.4% 之間平移。
**單一純量掃不進 band，代表誤差不是等比例的**，要嘛改成跟 glare 走的插值，要嘛換路線。

採用 R3 後產品頁實測 **46.65 fps**（43.43/48.14/48.40），中位 16.7ms、p95 33.4ms、`idleRaf` 0。
第四十三輪修掉主執行緒搶佔之後（見 §三），同一支腳本量到 **60.00 fps**（螢幕更新率上限），
中位 16.7ms、p95 16.8ms。

### R3 的實作要點

- 角色幀用 WebCodecs `ImageDecoder` 解出來，上傳成 **ImageBitmap** 材質
  （直接上傳 VideoFrame 會得到空白貼圖）。
- **不要開 `requestAnimationFrame` 迴圈**。素材時鐘用 `setInterval(33ms)`，
  指標事件只重畫當前幀。這樣 `idleRaf` 才會是 0。
- 疊化（待機↔特殊動作）靠 shader 的 `weight` uniform 讀兩張圖層的 opacity，
  不要在 JS 裡做逐格混合。
- three.js 要**內嵌並釘住版本**（0.160.1），不要走 CDN——卡面頁是自包含單檔。
  代價：單檔從 10.16 MB 變 10.55 MB。

### 遮罩仍然要留一份基準

即使執行期不用遮罩了，`build_gift_card.py` 仍產 15fps 遮罩當基準。
⚠ **驗收腳本要拿釘死的 90 格參考當基準**，不能拿產出的遮罩檔——
收了 15fps 之後那個檔就是 45 格，拿它當基準等於自己比自己，門檻會全過。

## 二、驗收工法（這一段比渲染更重要）

### 1. 每一條視覺門檻都要上下限成對

只寫上限＝做出看不見的東西。第三十七輪粒子只覆蓋 0.16% 卡面、整卡增亮 0.017%
（上限是 2%），每一條都通過驗收，使用者說「幾乎看不出來」。

但只補下限也不夠：**實作者會用最省事的方式去頂下限，而那個方式常常把東西做壞。**
第四十二輪為了過「亮度 ≥0.6%」，把白光暈疊了三層，指標過了但 16 顆愛心全糊成光斑。

所以完整的做法是：

- **量的門檻**（覆蓋率、亮度增量）上下限成對
- **形的門檻**跟著配：本體面積／幾何形狀面積比值（1.0–2.2）、與原始形狀的 IoU（≥0.55）
- 兩者都要，缺一個就會被鑽

### 2. 門檻要先量基準再訂，不要憑感覺挑整數

「亮度增量 ≥0.6%」這條是憑感覺訂的，事後證明**與「看得出是愛心」互斥**——
只有把愛心糊成光斑的版本搆得到。這是無效門檻。

正確順序：**先做一個「明顯合格」的樣本，量它的實際值，再往下留餘裕當下限。**
玻璃愛心實測亮度 0.296–0.351%，下限就訂 0.25%（留約 18% 餘裕）。

同理，「遮罩溢出 ≤0.40%」也曾訂錯——逐格基準本身就有 3.07% 的重採樣邊緣，
那條門檻連「什麼都不改」都過不了。改成**相對逐格基準的增量**（≤0.15 pp）才有意義。

**這個錯誤很容易重犯。** 第四十三輪又犯了一次：角色換格的靜止下限訂 30.0 格/秒
（因為某一次量到 30.5），實作者交出來 29.2 被判紅——但**拿修正前的頁面用同一把尺量，
是 29.92，一樣不過**。那條門檻擋不住任何東西，只是在標記雜訊。

> **驗證門檻本身有效的方法：拿「修正前的版本」去量。**
> 修正前也不及格 → 這條門檻沒有鑑別力，是儀器或門檻的問題，不是實作的問題。
> 這一步只花一次量測，卻能擋掉「追著假紅燈改東西」的整個分支。

配合 §3（拿已否決的版本驗證它還是紅的），一條門檻要同時通過兩個檢查才算可用：

| 檢查 | 拿什麼去量 | 應有結果 |
|---|---|---|
| 有鑑別力 | 已被否決／已知壞掉的版本 | **紅** |
| 不誤傷 | 修正前的版本、或已知合格的樣本 | 該綠的要綠 |

### 2b. 量測儀器要先暖機，否則第一個 run 不能代表任何東西

上面那個 29.2，成因是每個 run 都開新分頁，**第一個 run 要付 shader 編譯與貼圖上傳的成本**。
三個 run 是 27.09 / 30.25 / 30.25——只有第一個低。

修法：**在正式量測之前，先完整跑一輪然後把結果丟掉**（暖機頁）。之後靜止穩定在
30.25 / 30.42 / 30.25 = 30.31，門檻 30.0 一個字都不用改。

⚠ 光是「載入後多等幾秒」不夠——我試過等 4 秒，第一個 run 還是 27.44。
要的是**真的跑完一輪完整量測再丟棄**。

### 2c. 同一份頁面、同一台機器，不同量測設定會給出不同答案

第四十三輪同一份頁面的「移動時角色換格」，我量到的平均是
**28.17 / 26.46 / 25.00**，單次落在 23.6～28.3——差別只在量測窗長度與有沒有暖機。

所以：

- **絕對值不能當結論**，就算是自己量的、就算量了三次。
- 唯一可信的是**同一支腳本、同一次執行環境下，對「修正前 vs 修正後」的相對比較**。
  最後定案用的就是這張表（修正前 15.39 → 修正後 30.20）。
- 先把儀器釘死（暖機、窗長、取樣方式），再談數字。

### 2d. 「騎在門檻上」不算過

同一份頁面三組平均 28.17 / 26.46 / 25.00，門檻 27.0 剛好在區間正中間。
平均有時過、有時不過，這叫**騎在門檻上**，不叫通過。

門檻要寫成**雙重條件**才擋得住這種情況：

- 三次平均 ≥ 目標值（例：29.0，理想 30.3 的 96%）
- **且任一單次不得低於底線**（例：27.0）

把原本的「平均 ≥27.0」改成「平均 ≥29.0 且單次 ≥27.0」是**收緊**，不是放寬。

### 3. 改判準的取樣方式時，要先證明它還擋得住已否決的版本

換門檻的取樣方式（例如把本體的灰階 cutoff 從 >6 改成 >40）很容易變成變相放水。
**做法：拿已經被否決的版本用新尺量一次，它必須還是紅的。**

| 控制組 | 應有結果 | 實測 |
|---|---|---|
| 疊三層光斑版（已否決）| REJECT | 2.41–3.59 / IoU 0.279–0.414 → REJECT ✅ |
| 玻璃泡泡（選定）| PASS | 1.05–1.08 / IoU 0.892–0.921 → PASS ✅ |
| 實心＋4px 光暈 | PASS | 1.54–1.64 / IoU 0.610–0.648 → PASS ✅ |

這張表本身就是判準的一部分，要寫進驗收腳本，不是一次性的檢查。

### 4. 決定性取樣（沒有這個，紅綠都不可信）

- CSS 動畫用 **Web Animations API 暫停＋設 `currentTime`**，不要靠 `wait_for_timeout`。
- 動畫 WebP **不能用 WAAPI 定位**，要把圖換成解出來的那一格 PNG。
- 設定狀態後加**雙重 rAF 重繪屏障**再截圖，否則會截到上一格
  （第三十五～三十七輪各出現一次這種假紅）。

### 5. 正控制與負控制都要有

只驗「不該出現的東西沒出現」會被「量錯位置」偽裝成通過。
名字框遮蔽那條的做法：愛心像素必須 0（負控制），
**同時**把遮蔽條件拿掉後必須 >0（正控制，實測 29845）——證明量到了正確的區域。

### 6. 任何 fps 結論至少三次取平均，跨機器不能比

同一份頁面同一台機器，單次量到 23.9 / 25.6 / 23.9；另一輪同一頁量到 43.98 與 54.71。
公司那台的 21.0 跟本機的 24.5 **不能相減當作改善幅度**。

### 7. 判準的參考值要取「在地」的

驗卡片四角有沒有黑塊時，我拿左上角外的背景亮度去套四個角，
但頁面背景是放射漸層（上亮下暗），下面兩個角自然「不及格」——**製造了三個假紅燈**。
背景參考值要取各角落**緊鄰的**區域。

驗證腳本說「全部都壞」時，先懷疑判準寫錯。

## 三、幾個具體的坑

### 3D 堆疊裡是 `translateZ` 決定前後，不是 `z-index`

卡面是 `preserve-3d`。要把愛心放到名字框後面，只改 `z-index` 很可能完全沒作用。
**遮蔽關係要用像素證明**，不要只驗 CSS 變數。

### 量測用的輔助元素會漏進成品

為了讓「開 vs 關」對照的合成拓撲穩定，實作者在卡面鋪了一塊
`.gift-hearts:before{position:absolute;inset:0;background:#000}`，理由是「screen 混合下黑色是中性的」。

結果卡片圓角外出現**純黑（lum 0）的 L 形硬邊角**。機制：那塊底板是方角
（容器的 `clip-path` 是方形多邊形，沒有圓角），而容器有 `transform:translateZ(...)`
是獨立的 3D 合成層——**`mix-blend-mode:screen` 在圓角外沒有背景可混，就吐出純黑**。
screen 對黑色中性的前提是「有東西可以混」，獨立合成層的空白處不成立。

抓法：對改動前的版本做單一變數 A/B（HEAD 27／現況 0／只關那塊 26／整組拿掉 27）。

### 指標事件的處理會把非同步解碼餓死（fps 沒掉，但動畫掉幀）

第四十三輪：卡片跟著游標傾斜時，**角色動畫掉一半**（30.5 → 15.4 格/秒），
但頁面整體 fps、卡片傾斜本身都很順。使用者的描述是「角色部分幀數會微微下降，其他地方都很棒」。

原因是兩種東西跑在不同地方：

| | 跑在哪 | 移動時受影響嗎 |
|---|---|---|
| 卡片傾斜 | CSS transform，合成執行緒 | 不受影響 |
| 角色換格 | 主執行緒的 `ImageDecoder` 非同步解碼 | **被餓死** |

每次 `pointermove` 都同步跑一次 `HoloCardFace.paint()`（CSS 傾斜／反光更新），
佔住主執行緒，讓 33ms 的換格計時器一直撞上「解碼中」守衛而**整格跳過**。
而 **`pointermove` 的觸發率可以高於螢幕更新率**，所以同一個顯示幀內會重複 paint 好幾次，
那些都是白做的。

**定位方法（違反直覺的訊號）**：單一變數 A/B，把候選瓶頸停掉看是否恢復。
停掉 `paint` 之後角色回到 27.3 格/秒，而 **`draw` 呼叫反而從 52 升到 88**——
**畫得更多但更順，就證明瓶頸不在渲染。**

**修法**：`pointermove` 用 rAF 合併（一個顯示幀最多做一次）＋降低 paint 頻率＋預解一格。
結果 15.39 → 30.20 格/秒，與靜止同速；整體 fps 也從 46.65 上到 60.00。

⚠ **降頻要證明互動沒變頓，不能只看 fps。** 交「傾斜角度的時間序列」比對：

| | 有更新的幀 | 幀間變化中位 | 傾斜幅度 |
|---|---:|---:|---|
| 修正前 | 99–100% | 0.0141 | 0.3801/0.3809 |
| 修正後 | 99% | 0.0135 | 0.3803/0.3805 |

幅度相同代表沒被削弱、幀間變化沒變大代表沒變頓。這條做成 `check_gift_tilt_trace.py`。

⚠ 呼叫端可以改頻率，但 `card_face.js` 是**凍結檔**，不要改 `paint()` 本身。

### 共用卡框有一道接近純黑的描邊

`demo.html` 的 `.face-frame` 有五道 inset 描邊，第三道是 `#18101c`（rgb 24,16,28）。
在深色卡上看起來像陰影，**在淺色/粉色卡上就是突兀的黑環**（邊緣最暗 lum 41）。

要改就**在該卡自己的 rarity class 覆寫**（例如 `.r-special .face-frame{box-shadow:...}`），
換成同色系的深色（粉卡用 `#8a4a72`，邊緣最暗 lum 拉到 145）。
⚠ **不要改 `demo.html`**——那是所有卡面共用的凍結檔。

### `prefers-reduced-motion` 停不掉動畫圖片

瀏覽器不會因為 `prefers-reduced-motion` 就停掉動畫 WebP／GIF。
所以「減少動態」的判準**不能用整卡像素差**（會把角色動畫算進去，
改動前 106,940 / 改動後 127,022，同一個數量級）。
要**只量目標元素**：該層 `getAnimations({subtree:true})` 長度為 0、
可見數 >0、隔 1.5 秒 `getBoundingClientRect()` 不變。

## 四、名字框與文字

### 覆寫沒生效的徵兆：好幾個版本量出來一模一樣

要蓋掉卡框／名字框的樣式，**選擇器特異性要對**。
共用 CSS 裡有 `.hcard.r-special .face-plate{...!important}`（兩個 class），
寫成 `.r-special .face-plate{...!important}`（一個 class）是蓋不過去的。

我第一次量四個透明度版本，對比度全部是 11.21 —— **一模一樣就是覆寫沒生效**。
差點把「這個改動沒有影響」當成結論。

> **改樣式後第一件事是印出 `getComputedStyle` 確認真的變了**，再開始量。
> 這跟 §二 的「先驗證儀器」是同一件事。

### 名字框透明化：由下往上淡出，不是整塊降透明度

做法是把實心底換成 `linear-gradient(to top, …)`，底部保持不透明、上緣接近透明，
這樣框會融進畫面而不是壓一塊板子。禮物卡定案值：

```css
background:linear-gradient(to top,rgba(28,7,20,.72),rgba(43,15,36,.50) 52%,rgba(58,21,48,.15))
```

⚠ **會跟粒子的挖空打架。** 愛心層當初為了不透過半透明名字框，
用 `clip-path` 把卡片下緣挖掉一條。名字框變透明後，粒子會在挖空邊界**硬生生消失**。
兩者要一起改：拿掉挖空，讓粒子穿過名字框。

⚠ 名字框透明化會讓文字失去背景依靠，**文字對比度要重新量**，而且要量游標左/中/右三個位置
（透明之後底下透出來的是會動的畫面，不同位置底色不同）。

### 文字變色：conic-gradient 吃 `--phase`，位置吃指標

卡框的變色是 `conic-gradient(from var(--phase), …)`。文字要「像邊框那樣變色」就用同一套：

```css
background-image:conic-gradient(from var(--phase), …);
background-size:230% 230%;
background-position:calc(50% + var(--gift-edge,0)*34%) 50%;
```

⚠ **只轉角度是不夠的。** 禮物卡本來就有 `linear-gradient` 吃 `--phase`，
但在小面積文字上實測左右游標的字色差只有 **ΔRGB 4.87**——等於看不見。
改成 conic ＋ 跟著指標推 `background-position` 之後是 **43.61**，約 9 倍。

所以這條門檻要**上下限成對**：下限防「加了等於沒加」（4.87 就是活生生的例子），
上限防變成七彩霓虹燈。禮物卡訂的是 ΔRGB 20–80。

效能上是免費的：純 CSS 變數驅動、文字面積小，
實測角色換格 30.08 → 30.36 格/秒（沒有拖累，見 §三 那條）。

### 描邊：暗描邊是文字跟背景分離的關鍵，白色不能拿來當「描邊」

使用者覺得 `#21102c` 的描邊「看起來是黑的、不好看」。實測換色的代價：

| 描邊 | 名字對比度（游標左/中/右）| 結果 |
|---|---|---|
| `#21102c` 深紫黑（原本）| 8.3 / 11.3 / 7.6 | 清晰，但讀起來像黑色 |
| 純白 | 6.2 / 5.4 / 6.0 | 字失去輪廓變糊 |
| 淡粉 `#ffd6ea` | 6.4 / 5.1 / 6.1 | 同上 |
| 白＋淡暗底 | 5.2 / 4.1 / 4.9 | **低於 4.5** |
| 淡粉＋粉光暈 | 5.1 / 4.2 / 4.9 | **低於 4.5** |
| **莓紫 `#5c2148`** | **5.7 / 6.6 / 5.6** | 輪廓接近原本，黑感消失 |
| 深玫瑰 `#7a2b5c` | 4.9 / 5.4 / 4.9 | 更粉，接近下限 |
| 粉紫 `#8a4a72` | 4.4 / 4.3 / 4.2 | **低於 4.5** |

> **使用者說「不要黑色」時，答案通常不是「改成白色」，是「改成同色系的深色」。**
> 保留明暗對比、只換色相，輪廓就還在。

⚠ 用了 `background-clip:text` **就只能用 `drop-shadow` 疊描邊**——`text-shadow` 會被裁掉。

⚠ 卡框能用的顏色不一定能用在文字上：`#8a4a72` 拿去修卡框黑環很好，
用在文字描邊卻是 4.2–4.4，紅的。**每個用途都要各自量。**

⚠ **上表只否決了「白色當描邊」，沒有否決白色。**
白色用在**外光暈**是對的做法（見下一節），跟用在描邊是兩件事：
描邊要保輪廓、外光暈要把字抬起來。我當時把兩者混為一談，
量到「白描邊會糊」就結論「白色不行」，繞了好幾輪冤枉路。

### 名字框與文字的懸浮感：照「宇宙冒險羊」的配方

使用者說「字的懸浮感不夠、沒有像之前的卡那樣浮起來」時，
**先去量現有那張做對的卡，不要自己推**。我沒這樣做，於是推論出一條完全錯的路（見下面的死路）。

實測 `r-mythic` 的宇宙冒險羊（`rocketdog`）：

| 項目 | 實測值 |
|---|---|
| 畫面 `.face-art` Z | 36.4 |
| **名字框 `.face-plate` Z** | **13（比畫面還後面 23px）** |
| `transform-style` | 全部 `flat`（沒有任何 `preserve-3d`）|
| 名字／稀有度 Z | 0 |
| 名字框內縮 | 左右各 4.3%、下 12px、高 57.5px |
| **名字框投影** | `0 0 0 1px #0a0d15, 0 7px 18px rgba(0,0,0,.53), inset 0 1px 0 #ffffff18` |
| **名字 filter** | `drop-shadow(rgba(30,12,40,.9) 0 1px 0) drop-shadow(rgba(0,0,0,.85) 0 2px 6px) drop-shadow(rgba(255,255,255,.35) 0 0 12px)` |
| 名字漸層 | 整條彩虹 `conic-gradient(from var(--phase), 粉→橘→黃→綠→藍→紫)` |
| 稀有度 | `color:#d8fff0` ＋ `text-shadow:0 0 8px rgb(147,240,223)`（純光暈，沒有 filter）|

**懸浮感由三件事構成，跟 Z 軸無關：**

1. **名字框投影到畫面上**：`0 7px 18px rgba(0,0,0,.53)`。板子在畫面上投下影子＝板子在畫面前面。
2. **名字框內縮**（左右各約 4.3%）。滿版的一條看起來是「卡片的一部分」，
   內縮才像「壓在卡片上的一塊板子」。
3. **文字有白色外光暈** `drop-shadow(rgba(255,255,255,.35) 0 0 12px)`，
   配一道深色內描邊 `0 1px 0` ＋ 一道柔投影 `0 2px 6px`。
   **三層分工：內描邊保輪廓、柔投影給厚度、白光暈把字從板子上抬起來。**

這一套在透明名字框上也成立——`box-shadow` 畫的是 border-box，跟背景透不透明無關，
半透明板子加投影反而更像一片浮在上面的玻璃。

### ⚠ 死路紀錄：不要用 translateZ 去做名字框的懸浮

我一開始假設「懸浮＝把圖層在 Z 軸推出來、傾斜時產生視差」，花了好幾輪，結論是**行不通**：

- 禮物卡原本名字框 Z=38、畫面 Z=36.4，只差 1.6px，左右傾斜視差 0.42px（等於沒有）。
- 推到 Z=100 視差有 28px，但**透視放大 6.4%**，滿版的名字框直接穿出卡框右緣 16.7px。
- 更糟的是**文字會被名字框自己的背景蓋住**（對比從 6.58 掉到 3.57，
  `elementFromPoint` 驗證最上層變成 `.face-plate`）。
  成因：`.face-plate` 與 `.face-text` 都是 `transform-style:flat`，
  子元素被壓平在名字框的平面，推高之後繪製順序反轉。
- 要救就得把兩層都改 `preserve-3d` 並給名字／稀有度各自的 Z——
  改動面積遠大於直接加一道 `box-shadow`，而且**現有做對的卡根本沒這樣做**。

**先看成品怎麼做的，再決定要不要自己發明。**

## 五、派工工法

程式由 GPT-6 寫：`codex exec --sandbox workspace-write -m gpt-6-astra "<簡報路徑>"`，
用 ASCII 檔名的 `.cmd` 包起來背景跑。

- ⚠ **命令要加 `< NUL`**。不導 stdin 的話它會卡在
  `Reading additional input from stdin...` 那一行**無聲掛死**，log 停在 39 bytes、
  行程活著、不報錯、不逾時。同一份包裝前兩次能跑不代表這次不會卡。
  **派完要回頭確認 log 長到 500 bytes 以上**（有印出 workdir／model／session id 的抬頭）。
- 它的 commit 一定被 sandbox 擋（git index 在 worktree 外），由人複驗後再 commit。
- **它的驗收全綠也要自己截圖。** 第二十八輪拖曳變數全對但畫面整片藍；
  第四十二輪它的驗收全綠，但愛心全擠在卡片左半邊、右半邊一顆都沒有。
- 反過來，**它報紅的也要自己驗**。第四十二輪它自報「失敗交付」，
  實際上時間預算三條路全達標，它只是沒對 R1/R3 做增益校準就判它們失敗。
- 簡報裡要明寫「做不到就回報實測值停手，不要自己放寬預算」。
  它照做了——第三回它在形狀與亮度無法兼得時停手升級決策，沒有自己選一邊。

### 簡報要寫什麼

- 已經確認達標的部分要**列出實測值並寫「不要動」**，否則它會重做甚至弄壞。
- 門檻要連**為什麼是這個數**一起寫，它才不會當成可調參數。
- 它會鑽布林判定的漏洞：規格寫「每顆不同」，它就用 `i*0.02`、`i/15` 這種
  epsilon 遞增讓 16 顆的 size 全部落在 19.0–20.0px（區間是 11–20）。
  **區間的意思是要真的分散，這句話要寫出來。**
