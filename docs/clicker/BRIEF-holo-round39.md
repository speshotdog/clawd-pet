# 派工簡報（第三十九輪）：修掉魔花少女的卡頓

日期：2026-09-10。分支 `holo-cards`，工作區 **`D:\claude研究\clawd-pet-holo`**（git worktree）。
⚠ 路徑含中文，指令用相對路徑或先 `cd` 進工作區。

**本輪只動「魔花少女」這一張禮物卡。** 共用 CSS、`card_face.js`、卡池、抽卡頁不准動。
**本輪不加任何新效果**，只處理效能，並且**不准讓第三十六～三十八輪的任何視覺門檻退步**。

## 〇、起因與已完成的診斷

使用者回報：「卡片移動展示都變得很卡頓」。

我已經量過，**元凶不是第三十六～三十八輪加的東西**。逐項關閉測試（headless、
`--use-angle=d3d11`、viewport 900×1000、DPR 2、連續 `pointermove` 3 秒、rAF 逐格記錄）：

| 狀態 | fps | 每格中位 |
|---|---:|---:|
| 第三十八輪現況（4 支動畫同時跑） | 15.0 | 66.7ms |
| 關掉粒子與愛心 | 14.7 | 66.7ms |
| **關掉 alt 兩支動畫** | 23.3 | 33.4ms |
| **再關掉遮罩動畫** | **42.0** | **16.7ms** |

粒子、愛心、卡緣陰影、卡框 `filter`、transform 過渡、反光層**逐項關掉都在誤差內**。
兩個真正的成本是：

### 成因 1：待機時有兩支用不到的動畫一直在解碼（**這是我造成的**）

`build_gift_card.py` 的頁面 JS 在建立時就設了 `altImg.src = A['alt']`，
註解寫的理由是「沒有 src 的 `<img>` 會讓驗收腳本『等所有圖載入完成』的條件永遠不成立」。
結果就是**待機時特殊動作那支角色動畫與它的遮罩動畫一直在跑**，白白吃掉一半的幀。

**這是拿產品去遷就測試，方向反了。** 正確做法：待機時不要有 src，觸發時才設；
驗收腳本的等待條件改成「忽略沒有 `src` 的 `<img>`」。

### 成因 2：動畫遮罩每一格都讓整層重新光柵化

`mask-image` 吃 animated WebP 時，每一格新遮罩都會讓被遮罩的 600×840 圖層整片重算——
遮罩不像 `transform` 走合成執行緒。這一項單獨就佔了 33.4ms → 16.7ms 的差距。

---

## A. 修掉待機時的多餘解碼

- 待機時 `altImg` 不得有 `src`（或用等效手段確保它**不在解碼**）；
  觸發特殊動作時才設 `src`，並在疊化開始前 `await img.decode()`，避免第一格是空白。
- 對應的 alt 遮罩層同樣不得在待機時持有動畫遮罩。
- **驗收腳本要跟著改**：把「所有圖都 `complete && naturalWidth>0`」改成
  「**有 src 的**圖都載入完成」。不准為了讓等待成立而在產品上保留解碼。
- 疊化的既有門檻（進出各 ≥3 個中間值、不得空白格、不得雙層同時滿、互補和 ±0.025、
  回到常態端點）**全部不變**，而且要證明改完之後仍然過。

**預期**：中位 66.7ms → 33.4ms（實測值，見〇）。

## B. 處理動畫遮罩——**先量再選，不准用猜的**

三條路，**必須三條都量過再選**，報告要寫出每條的數字與你選了哪一條、為什麼：

1. **靜態剪影**（所有格 alpha 的聯集或第 0 格）。成本幾乎歸零，但箔面不再逐格貼合角色。
   ⚠ 這在 mtk 那張「頭被削開」的動畫上會露出明顯的發光殘影（已記在 `build_mtk_art.py` 註解），
   **但這張是輕微的呼吸晃動，位移小很多**，很可能看不出來——所以要量。
2. **降低遮罩的張數**（例如 30fps → 10～15fps，或抽格）。成本大致等比下降。
3. 維持現狀。

### 判斷靜態剪影可不可行的量法（硬性）

對角色動畫的**每一格**，量「遮罩涵蓋但該格角色 alpha=0」的像素數，換算成佔卡面的比例，
取所有格的**最大值**：

| 條件 | 門檻 |
|---|---|
| 靜態遮罩的最大溢出比例 | **≤ 0.40%** → 可以用靜態 |
| 0.40%～1.20% | 用做法 2（降張數），並回報降到多少張時溢出降到 ≤0.40% |
| > 1.20% | 維持逐格，改用其他方式省成本，並回報數字 |

同時要量：改完之後**箔面仍然貼著角色**——取第 0 格，遮罩與角色 alpha 的 IoU **≥ 0.95**。

## C. 效能預算（本輪的主門檻）

用下面這支量測方式（**請寫成 `_art/holo-test/check_gift_perf.py` 進版控**，
之後每輪都要能重跑）：

- headless Chromium，`--use-angle=d3d11`，viewport 900×1000，DPR 2
- 頁面載入完成後靜置 700ms
- 連續 3 秒：每個 rAF 對 `#stage` 派送一個 `pointermove`（座標沿橢圓繞行），
  同時記錄每格的間隔
- 取 fps、中位、p95

| 條件 | 門檻 |
|---|---|
| **每格中位** | **≤ 25ms** |
| p95 | ≤ 50ms |
| fps | ≥ 35 |
| 靜置（不移動游標）3 秒的 rAF 次數 | **仍然是 0** |

同一支腳本也要跑**搬移後的單檔**，兩邊都要達標。
若 B 選了做法 2 或 3 導致達不到 25ms，**照實回報數字，不要放寬門檻**——
那代表要回來討論是否犧牲逐格遮罩。

## 〇之二、不可以退步的保底（第三十八輪成品的實測值）

第三十八輪的 A／B／C 門檻**全部維持**，本輪要重跑並列出改前／改後：

- 粒子覆蓋率 ≥1.2%、整卡增亮 ≥0.30%、圖窗 2 秒差異 ≥1.0%、2 秒位移 ≥卡高 3%
- 愛心 8～12 顆、14～20px、透明度 0.45～0.65、IoU ≥0.80、垂直範圍 60%～80%
- 回彈過衝 8%～20%、回正 550～800ms、跟隨 90% ≤120ms
- 卡緣左右亮度差 ≥25 灰階且左右傾符號相反
- 卡名 ≥6.46:1、稀有度 ≥4.5:1、寶石 ≥145.67、置中 <2px、字級與文字框幾何不變
- 文字框粒子差異 ≤0.02%、`elementFromPoint` 不變、逐格投影超緣 ≤1.5px、reduced-motion 全靜止

**任何一項退步都算失敗**，不准用「為了效能所以視覺退一點」來交換——
效能要從 A、B 兩個真正的成本來源省，不是從已經驗收過的效果上砍。
