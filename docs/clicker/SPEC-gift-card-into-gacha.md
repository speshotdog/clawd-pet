# 另案規格：禮物卡（魔花少女）進抽卡系統

**狀態：只有規格，本輪沒有施工。** 沒有重建禮物卡、沒有動 mtk 單卡、沒有清理舊命名產物。

使用者 2026-09-11 的裁決原文：

> 「他是特別的 維持 並想辦法放入抽卡系統」

指令來源：`ORDER-2026-09-11-parity.md` 第 5 節（Astra 裁決本輪只交規格）。

## 一、目標與邊界

| 項目 | 內容 |
|---|---|
| 對象 | `mohuashaonv`，稀有度 `special`，產物 `_art/holo-test/gift-mohuashaonv.html` |
| 要保留 | 它的特殊卡框、文字效果、動態素材、互動——**外觀不改** |
| 要新增 | 讓它能透過抽卡系統取得 |
| **不含** | `mtk-card` 是另一份樣品，**不自動視為同一張卡、不一起進卡池** |

## 二、⚠ 「維持外觀」與「修字型」會不會打架：會，要先量

Astra 本輪直接解碼確認：

| 頁面 | Sans／Serif bytes | cmap |
|---|---:|---:|
| 主線九份（本輪重建後）| 240,448／325,236 | 739／739 |
| **禮物卡、mtk 單卡** | **996／984** | **0／0** |

也就是說禮物卡現在的卡名**跑的是系統 fallback**，跟主線修好之前一樣。
所以「重建禮物卡」不是無害的同步——它會**改變目前看到的樣子**。

**這一條要先做，再談整合**：
1. 先把禮物卡**現況**的合格外觀存證（實際平台字型、動畫、材質、互動，三尺寸截圖）。
2. 再決定「修字型」算不算破壞「維持」。這題**要問使用者**，不要替他決定：
   - 選項 A：連禮物卡的字型一起修好（卡名變成 Noto Sans TC，跟主線一致）。
   - 選項 B：禮物卡的卡名**維持現在的系統 fallback 外觀**，字型不動。
3. 不能把「換成有效字型」講成純同步、保證外觀不變——已經證明不成立。

## 三、整合要處理的四件事（不是把資料塞進 pool 就好）

1. **稀有度標籤**：`card_face.js:18` 的 `LABEL` 只有五階
   （common／rare／epic／legendary／mythic），沒有 `special`。
   要嘛補一個標籤，要嘛讓禮物卡走另一條顯示路徑。
2. **抽樣機率**：`build_deluxe_b.py` 的 `RATE` 是五階加總 1.0 的假機率
   （原註解已寫明經濟層還沒定案）。加入 `special` 一定會動到這張表。
3. **禮物頁獨有的渲染**：`build_gift_card.py` 有 `.r-special` 專屬規則
   （`.r-special .face-name`、`.r-special .face-rarity` 等）。
   卡面搬進抽卡的揭卡流程之後，這些規則要能跟著走——
   ⚠ 編隊那次的教訓：`body.` 開頭的選擇器跨不過 shadow 邊界（見 `team20.js` 的 `SHADOW_CSS`）。
4. **儀式演出**：揭卡演出是照稀有度分層的（`TILT`／`ZLIFT`／`SURGE` 都是五階表）。
   `special` 要對應到哪一層，或是自己一層，未定。

## 四、待使用者決定的產品規格（不要自己拍板）

- 抽取資格：任何時候都能抽到，還是限定活動／保底？
- 機率：`special` 佔多少？其餘五階怎麼重新分配？
- 重複取得怎麼處理？
- 抽到之後**可不可以編隊**？（編隊的四條累加上限是照五階排的，`special` 沒有位置）
- **不要自行把 `special` 映射成 `mythic`** —— 那等於偷偷改掉它的特殊性。

## 五、施工時的驗收要求（沿用既有工法）

- 保留 `METHOD-card-face.md` 的角色換格、傾斜、文字／銘牌與效果驗收。
- 整合必須走**真實揭卡流程**（`?ceremony-test` 固定序列指定抽到 `mohuashaonv`），
  證明特殊渲染在儀式裡仍然成立，不能只看靜態頁。
- 用本輪新增的 `check_card_parity.py` 收證據：
  禮物卡的「一致性」標準跟主線**不一樣**——它本來就該長得不一樣，
  所以要另外列一組「刻意不同」的清單，不能套主線的 parity 門檻。
- `build_gift_card.py` 末段會刪除舊命名產物，**執行前先列出實際命中的檔案**。
