# 直式手機版面：Astra 的分析與提案

日期：2026-09-08。這是討論提案，尚未實作。

我讀了原討論、目前工作區的 `src/clicker.css`、`src/clicker.html`、相關縮放／夥伴呈現程式與 `tools/test/clicker-round31.py`，並檢視 `r33-portrait-real.png`。下文的現況數字引用原討論；提案座標是計算值，不是新一輪真機量測。工作區原有的程式修改保持原樣。

我的主張是：錢包改成 60px 兩行、夥伴列收至約 100px、五個入口共用單行文字基線；舞台保留完整等比縮放，改用外部排序與留白把操作區放到下半部。不能把夥伴省下的高度直接算成舞台放大額度。

## 一、三個判斷，我同意什麼、要修正什麼

### 1. 錢包：優先級判斷對，溢出原因不對

`.wallet { margin-left:0 }` 並沒有被後面的規則覆蓋回去。真正留下來的是桌機定位：

- `clicker.css:195` 設了 `position:absolute`、固定高度、置中方式與裝飾內距。
- `clicker.css:332` 又設成 `left:340px; width:260px; padding:6px 20px`。
- 直式只改 margin、min-width、字級與 flex，沒有解除 position、left、width、height。

因此錢包仍脫離正常排列；topbar 改成 static 之後，它也不再是錢包原本的定位容器。x=340、寬 260 與殘留規則吻合，不是再補一個 margin 或 `!important` 就能修好的問題。

同意幣數最大、靠左。未來實作應在直式範圍內完整接管錢包的定位、尺寸與裝飾內距，也一併處理 `.rates` 繼承的 `min-width:100px`、右 margin。不要只修看到的那個屬性。

### 2. 空間：該拿掉夥伴列的 flex:1，但不能把 200px 換成舞台高度

390px 寬、左右各 8px 內距，舞台可用寬度是 374px：

`s = 374 / 608 ≈ 0.6151`，所以完整舞台高 `360 × s ≈ 221.45px`。

若把高拉到約 421px，等比寬度就會是 `421 × 608 / 360 ≈ 711px`。手機放不下；裁左右會丟場景與技能，單拉高度會變形。即使撤掉左右內距、用滿 390px，也只得到約 231px 高，增加不到 10px。

把外框加高、舞台仍只有 221px 可以做，但增加的是周圍留白，不是主角變大。也不能直接拉高 `#stage-fit`：現有 round31 明確檢查它維持 608:360。留白必須放在這個比例盒之外。

夥伴列也不宜直接定死 92px。目前角色卡高 88px，容器上下 padding 共 8px、邊框共 4px，最少需要 **100px** 才能原樣放下。92px 只剩 80px 內容高，會裁到卡片。我的第一版用 100px；若之後確實要 92px，就必須另做 80px 高的直式角色卡，重新檢查名字、星數與標記，而非只縮容器。

### 3. 分頁：同意文字統一，但不只移除圖示

現況同時有三種內容高度：圖示＋文字、只有文字、圖示＋文字＋名冊數量。單純把每顆按鈕內容整組置中，文字仍會落在不同 y。

建議直式五顆都用單行標籤：統計、場景、商店、換桌布、名冊。每顆 56px 高、字級先以 14px 評估，字級與 line-height 統一，文字本身水平及垂直置中。374px 扣掉四個 5px 間距，每顆約 70.8px，三字「換桌布」可以合理配置。

直式隱藏裝飾圖示即可，保留桌機原資產與結構。`#owned-count` 不再另佔底部一行；名冊數量放在名冊面板的標題或摘要，先確認那裡確實有等價資訊。保留場景目前的 disabled 狀態，不把它畫成能切換的入口。

## 二、844px 的建議分配

### 先定義高度，避免安全區扣兩次

原量測 topbar 在 y=6、footer 底在 838，顯示當次頁面沒有額外占用 47＋34px 的 CSS 安全區；不能直接把那組座標當成已含瀏海與 Home 區的量測。

以下按照題目要求，**假設 844px 是涵蓋上下安全區的可用 viewport**，保守預留上 47、下 34，另保留原本上下各 6px 外距。實作時必須用實際 viewport 與 safe-area 值，不能把 47／34 寫死，也不能在瀏覽器已扣除的區域再扣一次。HTML 目前未宣告 `viewport-fit=cover`；是否需要調整應由實機顯示模式驗證，不能僅憑截圖認定。

### 首選：升級／招募在上，舞台接近底部

排列為「錢包 → 可伸縮桌面留白 → 三條升級／招募 → 舞台 → 夥伴 → 五入口」。保留原舞台比例，不在內部重新排場景。

| 區段 | 高度 px | y 起訖（約） | 理由 |
|---|---:|---|---|
| 上安全區 | 47 | 0–47 | 題目給定的保守預算 |
| 上外距 | 6 | 47–53 | 避免貼住安全區邊緣 |
| 錢包列 | 60 | 53–113 | 主幣數一行，收益資訊一行 |
| 間距 1 | 7 | 113–120 | 分隔資訊與桌面 |
| 可伸縮桌面留白 | 96.55 | 120–216.55 | 把主要操作群往下推，不增加夥伴卡背景高度 |
| 間距 2 | 7 | 216.55–223.55 | 留白與操作群的邊界 |
| 升級／招募三條 | 182 | 223.55–405.55 | 3×56＋2×7，保留購買區觸控空間 |
| 間距 3 | 7 | 405.55–412.55 | 購買與拆包區分開 |
| 舞台比例盒 | 221.45 | 412.55–634 | 374×360/608，不裁切、不拉伸 |

這裡刻意承認有約 97px 留白；它的用途是把拆包操作群定位到下半部。以原本牛皮紙背景延續即可，不新增一塊看似有功能的大框。可以在這段顯示原本被隱藏的「下一目標」簡短提示，但不要為填滿高度新增任務或廣告。短螢幕時這一段先收掉，提示也不可成為新的固定高度負擔。

這會改變玩家看到的區塊順序：購買放上方，主要反覆點擊放下方。這是有取捨的提案，不是唯一正解。若產品必須保留「先舞台後商店」，則可把同一段外部留白放到舞台前面，仍保留 221.45px 舞台；但舞台與技能會比首選再高 189px，單手操作較吃力。我較支持首選。

### 技能槽是否落在拇指範圍？

原討論引用 `bottom:20px`，但 `clicker.css:381` 後來已覆蓋為 **`bottom:72px`**。現況應用 72 計算，不能為了配合討論數字把它改回去，否則可能碰到下方進度條。

64px 技能按鈕縮放後約 39.37px。按 72px bottom，槽內部頂部是 `360−72−64=224`、中心是 256；外部位置為：

- 本提案技能按鈕頂部約 `412.55 + 224s = 550.34px`。
- 中心約 `412.55 + 256s = 570.03px`。
- 底部約 `412.55 + 288s = 589.71px`。
- 四槽整體視覺寬為 `304s = 187px`，約落在 x=25.22–212.22，不會右溢。

原量測舞台 y=59，技能中心則約在 y=216.47，偏上；這份配置讓它往下移約 354px。它沒有掉出畫面，垂直位置也更接近下半部，但**不能光看 y 就保證左右手都舒適**：四槽集中左側，右手仍需跨到左邊。技能名稱與冷卻標記也可能超出按鈕本體，上述只計按鈕幾何。

我的觸控設計目標是實際可按範圍約 44px；這是提案目標，不是已通過的宣稱。現在視覺只有約 39px，320px 寬時還會縮到 32px。若不動舞台內部座標，可評估在直式增加透明命中延伸；必須確認它不重疊鄰槽、換夥伴入口、拆包區或每日禮包。不要把按鈕視覺加大後遮住場景當成預設解法。左右手實機單手連點與四槽操作，是採納首選前的重要驗證。

### 不同高度的收縮策略

844px 只是範例，不能把每個 y 寫死。令實際寬度為 W、高度為 H，舞台高為 `(W−16)×360/608`；外部留白吃掉固定區段以外的正剩餘空間。若 safe-area 實際為零，同樣 844px 會多出 81px，這部分留在上方，舞台與底部仍成為一組靠下排列。

在本表 390px 寬、81px 安全區的假設下，拿掉 96.55px 留白後，固定成本仍約 747.45px（保守保留五段間距）。更短時先縮減外距／間距；仍不足就讓中間內容局部垂直捲動，固定保留五入口。局部捲動與夥伴橫滑需測試手勢方向。不要依賴目前 `overflow:hidden` 把底下內容截掉，也不要再讓夥伴容器被 flex 壓扁。極短尺寸可能無法同時全顯所有控制，應明確接受可捲動降級。

## 三、錢包的四樣資訊具體怎麼排

我選 **60px 兩行**，不是把四樣都橫排成一行。

| 位置 | 內容 | 建議尺寸／對齊 |
|---|---|---|
| 左側第一行 | 錢幣圖示＋`1.00垓` | 幣圖約 22px，數字約 24px、行高 28px；整組靠左、垂直居中 |
| 左側第二行 | `每次 132.5億`　`每秒 132.5億` | 約 12px、行高 18px；兩組在同一基線，固定間距約 12px |
| 右側跨兩行 | 音量按鈕 | 約 44×44px、置中；音量面板向左展開並限制在 viewport 內 |

以 374px 外寬、邊框各 2、內距左右各 10、音量 44、欄間距 8 計算，資訊欄約有 **298px**。60px 扣邊框 4、上下內距共 8，內高 48；28＋18 的兩行可容納，還有 2px 行間距。收益兩組按 12px 字估算共約 160–190px，與幣數不再競爭同一行。

46px 不是幾何上絕對不可能：解除桌機定位、幣數 19px、收益用目前的小字上下堆疊，有機會塞進 390px。但這代表小字與較小音量按鈕，遇到 320px、字體載入切換、較長數值就更緊。若堅持四樣真正同一行，還需要左右 padding、幣圖與間距，沒有足夠餘裕保證大字可讀。多花 14px 換穩定結構更值得。

這些寬度是字級估算，必須以專案 Huninn 字體量測確認。測試不只放「1.00垓」，也要放格式器可能產生的長整數部分、`999.9…` 的單位交界、兩個收益同時很長的狀態。數字與單位不得斷行，也不能用省略號藏掉關鍵幣數。必要時窄屏先降低主幣數字級到約 22px，仍不足則增加錢包高度並從留白扣回，不縮整頁。

「置中」應分清楚：幣數整組靠左，但圖示和數字在同一行對齊；收益共用基線；五入口才是文字真正置中。不要把所有內容都設 text-align:center 當成修復。

## 四、原討論未涵蓋、但會影響成敗的問題

### 1. 橫滑不能取代尚未載入的夥伴分頁

`clicker-stage.js` 的 `setPartners()` 仍用 `ids.slice(page*10, page*10+10)`，每次只建立 10 位角色；直式卻隱藏 `.buddy-header nav`。滑到最後也不會出現下一頁未產生的角色。這不是半顆頭像的美觀問題，是入口不可達。

若未來只做 CSS，必須保留可用的前／後頁控制並重新分配列寬或列高；不能宣稱滑動已涵蓋全部夥伴。首選體驗是直式橫滑列包含全部已擁有角色，保留桌機的原分頁行為。這需要之後明確限定直式的呈現邏輯調整，**本次不實作**。

半顆頭像可以是橫滑提示，但應在夥伴內框邊緣被裁切，配合一致留白、淡出或簡短滑動提示，停止滑動時可吸附到完整卡片。驗收看的是最後一位能不能完整滑入、名字與星數是否可讀，不是所有滑動子元素的 bounding rect 都必須永遠在 viewport 內。

### 2. 特效「相同比例」不等於「相同原點」

HTML 中 `#click-fx`、`#floaters`、`#join-flight` 是 `#game-content` 的子元素，與舞台外框同層，不在 `#stage` 裡。直式 CSS 把它們放在 `left:0; top:0`，舞台卻在錢包下面；所以只共用 `--stage-fit` 並不能保證貼在同一位置。

另外 canvas 的 HTML 繪圖緩衝仍是 960×640，CSS 盒子改成 608×360；兩者比例不同。加入夥伴飛行還有 `game.width/960` 的座標換算。這些都是已看到的程式結構，實際偏移程度仍需按特效流程量測，不能直接斷言每種效果都壞掉。

未來移動舞台時，要一併驗證特效容器原點、CSS 縮放與 canvas 邏輯尺寸，並檢查從舞台飛向夥伴的跨區動畫。解法應處理外層座標映射，不更動 608×360 的場景座標。這也是不能只調 flex 排序就宣布完成的原因。

### 3. 其他殘留桌機尺寸與資訊消失

- `.buddy-header` 留有 900px 寬；即使 header 高變成 0，也應清掉直式不需要的固定寬度。動態 `#share-offer` 還有 `left:604px`，且 `#team` 改 static，定位參照也要追查。
- 三條購買列含較長價格、等級、招募與五連兩顆按鈕。截圖已看到招募價格換行；「三列 56px」成立的前提是實測長價錢仍可讀且按鈕不互蓋。中間標題欄要能收縮，數值與操作欄要有明確寬度策略；若必須增加招募列高度，從上方留白等量扣回。
- 直式隱藏 `#save-status`、`#retry-save`、`#notice`、`#next-goal`、`#pity` 和「最多」購買入口。不能把儲存失敗／重試、招募保底、批量購買一起當裝飾刪掉。各項應有可找到的替代入口；存檔錯誤可用平時不占高度的狀態提示，出錯時提供重試。
- `IMG x=-6` 尚不能判斷是哪個節點。`#stage` 後續規則已是 `overflow:visible`，裝飾確實可能突出。先記錄該圖的 id/class、祖先與用途，再決定只裁裝飾、保留陰影，或修正互動區。不要全域把舞台 overflow 改 hidden，誤切技能標籤與特效。

### 4. 斷點、順序與面板需要回歸確認

`max-aspect-ratio:3/4` 並不等於所有直式螢幕：較方的直式裝置可能不套用；瀏覽器工具列或鍵盤讓高度下降時也可能跨斷點。CSS 與 JS 現在共用條件，若日後調整，兩邊必須一致並保住 960×640 桌機。這次先記為邊界測試，不順手擴大規則。

若只用 CSS order 把商店放到舞台上面，鍵盤焦點與朗讀仍按 DOM 原順序走。首選在視覺上可行，但實作時必須同時解決直式閱讀／焦點順序；不能靠一串正 tabindex 補洞。若需要直式專屬 DOM 順序調整，就在尺寸切換時恢復桌機原順序，且回歸事件綁定與進行中的動畫。這是首選方案的實作成本，若後續堅持只准 CSS，可先採保留順序的折衷版。

現有底部推上的面板與技能切入橫幅保持原設計。只驗證面板底部操作、安全區、關閉方式與內部捲動仍可用，不重新設計面板。

## 五、後續實作邊界與驗收提議

桌機 960×640 的既有 CSS 規則、舞台內部座標、最多四槽，以及底部推上的面板行為皆保留。新增外部排版只作用於直式；若需 JS 處理夥伴完整列表、閱讀順序或特效映射，也只能在直式啟用，不能藉此重構桌機。

實作驗收仍必須執行題目指定命令：

`PYTHONIOENCODING=utf-8 python tools/test/clicker-round31.py`

PowerShell 對應方式是先設 `$env:PYTHONIOENCODING='utf-8'`，再執行 `python tools/test/clicker-round31.py`。不得放寬既有舞台比例、五入口與面板斷言來讓提案通過。

但這支測試不能單獨證明新版沒問題：它的 `wide` 只掃 `#game-content` 直接子節點，漏了錢包等後代；四槽只驗數量，沒有驗完整可見、命中與遮擋；也沒模擬真機安全區。因此後續還要針對這次風險做下列確認：

1. 390×844、320px 寬短屏、較寬手機；含瀏覽器工具列展開／收合、實際 safe-area，以及橫直切換。一般高度全顯；極短高度能捲到所有必要操作。
2. 同時放入長幣數、長每次／每秒、長購買價格與名冊數量；等字體載入後量測文字邊界及基線。
3. 四槽的名稱、冷卻、命中範圍都可用，左右手單手試點；每日禮包、多包與 Boss 狀態沒有新遮擋。
4. 夥伴超過 10 位時第一位、最後一位皆可到達；零夥伴、新加入、寄生與槽位標記也不被 100px 列裁掉。
5. 浮字、粒子與加入飛行對準來源／目的地；儲存失敗可見且能重試；五入口文字對齊且面板維持原開啟方式。
6. 桌機 960×640 與 exe 外觀、操作保持原樣，並保留 round31 的橫式驗收。
