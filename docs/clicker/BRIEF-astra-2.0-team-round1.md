## 〇、先做的小修：手機識別物那條門檻換掉

第三輪唯一的 FAIL 是 `390x844.landmarks_visible 10.459%`（我訂的下限 12%）。

**使用者已確認手機那張圖認得出是後院。** 所以那條門檻量錯了東西：
它量面積比，但目的是「認不認得出來」；窄螢幕必然把兩側的識別物裁掉，
而「識別物擺兩側、中央留乾淨」是我自己訂的構圖規則——**兩條規則互相打架**。

換成**直接量目的、而且比原本更嚴**的一條：

- **走完第一段的整個捲動行程中，三個識別物「每一個」都必須至少完整出現過一次**
  （單一捲動位置下，該識別物包圍框可見比例 **≥ 90%**，上限 100%）
- 面積比那條保留但降成**軟門檻**：手機 `landmarks_visible` **≥ 8%**（上限 25%），
  低於 8% 才算 FAIL

⚠ 原本的 12% 是我訂的，我自己撤換並說明理由——**這不是你可以自行調門檻的先例。**

## 二、卡從哪來

- 原型只要 **20～24 張**，**四個階級都要有**（mythic／legendary／epic／rare 各至少 4 張）。
  其餘之後再接，**在畫面上標明這是原型子集**。
- 卡面走 `card_face.js` 的既有掛載方式（`observe` / `refit` / `unobserve`），
  **卡內幾何、Z、字級改動 0 項**。
- 單檔自包含仍然不可破。**檔案上限這一輪放寬到 6 MB**（地圖是 2.5MB）。
  卡圖以 WebP data URI 內嵌，`build_map20.py` 就地擴充。

### 階級對應（我的判斷，先照這個做，之後可改）

規則只有四階（神話／傳說／史詩／精良），卡池有五種稀有度：

```
神話 = mythic     傳說 = legendary     史詩 = epic     精良 = rare + common
```

`common` 只有 3 張，併進最低那一層。**在回報裡標記這是暫定對應。**

## 三、四條累加上限（先做這個，規模最小、價值最高）

固定顯示四列，**直接把集合寫出來**，不要寫成四種獨立配額：

```
神話                  n / 2
神話＋傳說            n / 6
神話＋傳說＋史詩       n / 12
全隊                  n / 20
```

- 每列高 **24～36px**，文字 **13～15px**、對比 **4.5～7:1**
- 每列配分段容量條（分段刻槽，不要連續填色——那是戰鬥進度用的）
- 新增預覽時**同時標示它影響的哪幾列**，回饋在 **100～160ms** 內出現

**超額時**：

- 原隊伍不變，卡片返回起點 **180～240ms**
- 在該列旁顯示具體句子，例如**「神話＋傳說合計已達 6，加入後將為 7」**
- 超額列邊框亮 **240～360ms**、線寬 2～3px、對比 4.5～7:1
- **文字持續到下一次操作，不是只閃一下**
- 多條同時違規要**全部標出**，先說最直接阻擋的那條

⚠ **驗收一定要包含混合隊伍**：已經帶了神話的時候會更早撞到第二條，
不能只測「純傳說第 7 張」那個特例。

## 四、版型

**不要擴充 `CeremonyTable.layout`**（它多排定位仍以兩排為中心，桌面卡寬有 170／190px 下限，
手機用 `.page-away` 做單卡瀏覽，都不適合比較隊伍）。另寫編隊專用版型模組。

| 情境 | 配置 |
|---|---|
| 1440×900 | **10 欄 × 2 排**，卡寬 88～104px，間距 8～12px |
| 1024×768 | **5 欄 × 4 排**，卡寬 88～104px；不夠時卡區獨立捲動，**容量列與技能列保持可見** |
| 390×844 | **4 欄**，卡寬 68～80px；不夠時降欄數，**不再縮小** |
| 詳情 | 選中後展示**未修改的完整卡面**，寬 240～304px |

- 滿隊項目數 **20／20**
- **任一卡的識別區被相鄰卡遮住 0～0%**
- `dealDuration:620` / `stagger` 留在抽卡，**編隊不要逐張發牌**

### 總覽用代理圖、詳情用完整卡面

代理圖保留 **5:7 外形、角色主要輪廓、稀有度符號、外部姓名**。
它是**另一個 UI 元件**，不是把凍結卡面的字級或 Z 改小。

- 角色主要輪廓占代理圖面積 **45～70%**
- 姓名字級 **12～14px**、對比 **4.5～7:1**
- ⚠ **不採「一律裁臉」**：會截掉兔子的槌、龍的角這種識別物
- ⚠ **68px 不是已證實的辨識下限**，這需要實機量。
  「隱去姓名後配對原卡的正確率 90～100%」要**由使用者判定**，
  **不要自己宣稱辨識率，也不要用像素差冒充**

## 五、卡片承載：這一輪的核心

`PLAN-2.0-visual-C.md` 第二節的成因判斷：
**不是「平面 UI 讓卡像廣告」，而是周邊沒交代卡由誰承載、與哪個操作有關。**
所以要連續的是**承載與操作關係**，不是材質密度——**卡可以比 UI 華麗。**

首版做三招（**第五招「承載槽跟隨反光」不要做**）：

| 招 | 做法 | 驗收 |
|---|---|---|
| **同一組選取關係** | 代理圖／詳情標頭／「已編入・替換」共用**編隊序號與側邊標記**，選卡時**三處一起換**（不能只同步換顏色）| 序號與卡片身分一致 **100%**；玩家由詳情指出隊伍位置正確率 **90～100%**（使用者判定）|
| **卡外承載槽** | 卡放在與容量列、技能格**共用導軌**的霧面槽板；用**卡外接觸陰影與槽底**交代位置，**不在 `.face-*` 裡加框或黑條** | 卡與槽內緣間距 **8～16px**；**卡被裁切 0%**；完整卡占詳情區 **35～50%** |
| **只在交界增加材質** | 槽板帶刮痕與邊緣明暗；一般文字與按鈕保持乾淨，**不把 `foil-stack` 複製到全站** | 有紋理表面占非卡片 UI **12～22%**；紋理開關在空白樣區灰階差 **6～14／255** |
| **節制外部動態** | 完整卡保留材質互動，**代理圖靜止**；選取用槽標改變 | 接受材質互動的詳情卡 **1 張**；自動掃箔與導航觸發揭卡 **0 次** |

## 六、技能四格（只做殼，不要發明機制）

四格固定在隊伍區下方，格高 **56～72px**、間距 8～12px。

- 格數 **4／4**
- **神話技能最多 1 張是硬限制**：第二張神話技能可被確認加入 **0～0 次**
- **技能來源尚未定案**，所以：標示「獨立技能」、有自己的挑選入口、**不畫連線**
  （連線會暗示必須由隊伍供應，那是還沒決定的事）
- ⚠ **不要畫戰力百分比條、冷卻條、能量條**——技能戰力定義還沒有，
  畫了就是先替未來機制下決定。虛構計量元件 **0 個**

| 門 | 通過帶寬 |

### 並排圖規格（照 `PLAN-2.0-visual-C.md` 第二節）

先固定分母：**詳情區 D**（預先標定，開關圖不得縮小它湊比例）、**卡片 K**（中立姿態投影，
不計槽、陰影、外光）、**非卡片 UI**（面板與控制的面積聯集）、**接合區 R**（卡外側 8～24px 的槽板，排除文字）。
兩張圖用**完全相同的遮罩**。

- 1440×900／1024×768／390×844 各拍一組，**手機不准縮成縮圖**
- 同隊伍、同卡、同游標位置、同動畫時刻
- 涵蓋各稀有度與 `depth／flat／framed`、亮暗卡都要
- **左＝關**（保留完整卡與功能，只關掉承載／接合材質／共同選取標記，**空間仍保留**），**右＝開**
- **另交各項獨立開關圖**（不然不知道是哪一項造成差異）
- 靜止／游標偏左上／偏右下三次取樣，**要等真的重繪**
- ⚠ **卡的大小、亮度、飽和度、文字、箔面參數一律不准為了右圖好看而動**
  （驗收項：對齊後卡內核心區的開關差異 **0%**）
