## 〇、使用者裁決（覆蓋上一輪「三個體積選項等裁決」那題）

> 「我的目標其實是希望一模一樣。」

**不要再給解析度選項了。** 使用者要的是三面的卡圖**完全相同**，體積代價他接受。

### 核心做法：一份編碼、全線共用

上一輪量到的差異（宇宙冒險羊 team 2.31／gacha-standalone 4.16／pool-standalone 3.58）
**成因不是解析度不夠，是每支建置腳本各自重新編碼**：
`build_cards_remade_standalone.py` quality 84、`build_deluxe_b_standalone.py` quality 82、
`build_map20.py` quality 90。三份不同的編碼結果 decode 出來當然不一樣。

所以要做的是：**卡圖只編碼一次，產出一份權威資產（600×840），
抽卡／卡冊／隊伍編制，一般版與離線版，全部嵌入完全相同的那串 bytes。**

這樣「像素相同」是**結構保證**，不是靠事後比對湊到門檻以下。驗收也要照這個邏輯寫：
- 先驗**資產同一性**：每個入口內嵌的卡圖 data URI，逐卡比 SHA-256 必須完全相同
- 再驗像素：同一串 bytes 解出來的像素本來就該 0 差異，拿它當回歸守衛

⚠ 不准用「兩份不同編碼但都夠像」來達標。目標是同一份。

### 體積上限可以放寬（唯一一條授權放寬的）

`build_map20.py:113` 的 `6_000_000` 是**腳本自己寫的預算**，
放不下就把地形品質從 94 一路降到 78——這不是平台限制。**授權你提高這個數字**。
但要：
1. 把新上限與理由寫在程式註解與報告裡
2. 報告列出**地形實際用到的 quality**（如果因此不再降級，要講清楚地形也跟著變好了、檔案變多大）
3. 其他離線版若也有體積門檻，一併列出舊值／新值／實際 bytes

除此之外**其他門檻一律不准放寬**（幾何、字級、稀有度 fallback、hover、裁切、像素重現性 mean<1.0）。

## 一、使用者另外問的：「做成快取、指上去才播放，可以省效能嗎？」

**先把兩件事分開，不要混答。**

- **檔案大小：省不到。** 離線版是單檔全內嵌（`cards-remade-standalone.html` 有 66 個
  `data:image/png`、71 個 `data:image/webp`、1 個 svg，**外部 `src` 0 個**）。
  bytes 已經在檔案裡，延後 decode 不會讓檔案變小。
- **執行期效能：有機會省**（記憶體佔用、decode 時間、待機 fps）。
  第 39 輪就是用同一招把待機 fps 15.3 → 21.0。

**所以這件事當獨立的效能工作做，並且有一條硬性限制：**

⚠ **不准做成「平常顯示縮圖、hover 才換高清」。**
那會出現「先糊後清」，跟「一模一樣」直接衝突，使用者會退件。
只允許「**同一張高清圖延後 decode／延後進 GPU**」，任何一個時間點使用者看到的畫面都必須是最終樣子。

要做就要量，並附數字：
- 卡冊在 1440×1200／390×844 的**初次可見時間**與**待機 fps**（前後對照）
- JS heap 與 decoded image 記憶體（前後對照）
- 驗「任一時刻都沒有出現低解析度中間態」——逐幀取數字，不要用 GIF 判讀
- 若量出來省不到或造成閃爍，**就寫「不採用」並附數據**，不要硬上
